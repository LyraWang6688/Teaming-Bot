## 一、三个问题的直接回答

| 问题 | 回答 | 依据 |
|---|---|---|
| 闭环应该跑在哪？ | **服务器** | 事件订阅必须常驻，见第三章 |
| MCP 应该放服务器还是本地？ | **服务器提供，宿主接入** | 同上；本地 MCP 只是薄壳 |
| 宿主承担什么？ | **用户触点**（问报告、看状态、触发分析） | 闭环不依赖宿主在线 |

**一句话**：闭环的核心（事件接收 → 分析 → 推送）必须在服务器；豆包工作 / WorkBuddy 是用户看得见的那一层，不是链路的承重墙。

## 二、当前已跑通的链路（生产在线）

生产地址：`https://meeting.bamamei.online`（实测 HTTP 307 在线）

```text
① minutes.minute.generated_v1  ← 飞书妙记生成事件（推送型）
      ↓ WSClient 长连接（服务端常驻）
② meeting_pipeline_tasks       ← 先落库、幂等去重
      ↓ worker 领取
③ /vc/v1/meetings/{id}         ← 会议详情
④ /minutes/v1/minutes/{token}  ← 妙记信息
⑤ /minutes/v1/minutes/{token}/transcript
      ?need_speaker=true&need_timestamp=true&file_format=txt
      ↓
⑥ 分析引擎（两阶段：证据提取 → 报告写作；Zone 决策树）
      ↓
⑦ meeting_records 持久化 + 永久报告链接
      ↓
⑧ 飞书机器人卡片推送 ／ 多维表格写回
```

**这条链路已经成立，不需要重做。** 本设计要解决的是「怎么让第二个、第三个人用上」。

## 三、为什么事件监听必须在服务器

这是本设计的**决定性约束**，来自 `lark-cli` 官方文档的明确警告：

> Avoid `kill -9` on consume processes for EventKeys whose PreConsume **registers a server-side subscription and unsubscribes on exit** (minutes, vc, board keys)

### 推论

| 事实 | 后果 |
|---|---|
| 妙记生成事件属于 minutes 类 | 属于「消费时注册订阅、退出时注销」的类别 |
| 本地 `lark-cli event consume` 是一个**前台进程** | 进程不跑 = 服务端没有订阅 = **一条事件都收不到** |
| 本地 event bus daemon 只是 UDS 本地 IPC 枢纽 | **不缓存离线事件**，不是事件仓库 |
| 用户机器不会 7×24 常开 | 真实用户场景下必然大面积漏收 |

**关键区别**：这不是「漏几条」的问题，而是「没跑消费者就完全没有订阅」。

### 对比

| | 服务器常驻 | 用户本机常驻 |
|---|---|---|
| 事件订阅是否持续 | ✅ 是 | ❌ 取决进程在不在 |
| 机器不开机 | ✅ 无影响 | ❌ 全漏 |
| 谁负责运维 | 我们 | 每个用户 |
| 真实用户可接受度 | 高 | **低** |

### 一个已知缺口（服务器方案也有）

WebSocket 长连接**不补发**断线期间的事件。若服务器在妙记生成的那一刻宕机，该事件会丢，且 `recoverFeishuMeetingPipelinesOnStartup()` 只能恢复**已落库的任务**，无法恢复从未到达的事件。

**建议补一个对账兜底**：定时拉取近期会议列表（接口 `POST /vc/v1/meeting/search` 或 `lark-cli vc +search` 等价接口），与 `meeting_records` 比对，补齐缺失的会议。这不是替代事件驱动，而是给事件驱动加保险。

## 四、目标架构

```text
┌─ L3 宿主（豆包工作 / WorkBuddy / Codex）────────────────┐
│  用户触点：问报告、看状态、触发分析、看推送              │
└────────────────────────────────────────────────────────┘
              ▲  MCP（远程 HTTP 优先，见第五章）
┌─ L2 MCP 层（服务器提供）──────────────────────────────┐
│  tools: doctor / whoami / list_reports / get_report /  │
│         get_pipeline_status / rerun_analysis           │
│  鉴权：设备授权码 → 长期 token（每用户独立）             │
└────────────────────────────────────────────────────────┘
              ▲  内部调用
┌─ L1 闭环核心（服务器，已在生产运行）────────────────────┐
│  飞书事件订阅 → 任务落库 → 文字稿 → 分析 → 报告持久化    │
│  → 飞书卡片推送 / 多维表格写回                          │
│  ★ 闭环 100% 在这里完成，不依赖宿主在线                  │
└────────────────────────────────────────────────────────┘
```

**要点**：L1 的可靠性与 L3 是否在线完全解耦。用户不开豆包工作，报告照样推到飞书。

## 五、MCP 形态选择

豆包工作的连接器体系原生支持三种传输（源码确认）：

```text
STDIO（本地子进程） / STREAMABLE_HTTP（远程） / SSE_HTTP（远程）
```

| 形态 | 用户安装成本 | 闭环可靠性 | 生态上架 |
|---|---|---|---|
| **远程 HTTP MCP**（推荐先做） | 填一个 URL | ✅ 不依赖用户机器 | 自定义连接器可用；生态上架要求见下 |
| 本地 stdio MCP（npx 包） | 装 node 包 + 配凭证 | ✅ 闭环仍在服务器，只影响查询 | ✅ 符合豆包 MCP 生态要求 |

### 建议节奏

1. **内测阶段**：远程 HTTP MCP。用户只填 URL + 走一次授权，零安装。
2. **上架阶段**：再补一个 stdio 薄壳包（`npx -y`），内部仍调服务器 HTTPS API。这是豆包 MCP 生态准入的硬要求（「运行时优先 npx」）。

> 注意区分两套分发规则：**自定义连接器**用户自配、免审核，支持 HTTP；**MCP 生态上架**需准入，要求 npx 启动。

## 六、多用户 onboarding（当前最大产品风险）

现状：每个用户通过 `registerApp` **创建自己的飞书应用**，再走六段门禁（创建应用 → OAuth → 选组织 → Base 校验 → 妙记订阅 → 长连接）。

对真实用户来说，**这套流程过重**。三个候选方案：

| 方案 | 说明 | 优点 | 代价 |
|---|---|---|---|
| **A. 维持自建应用**（现状） | 每用户一个飞书应用 | 无需飞书审核，权限最干净 | 步骤多，普通用户走不完 |
| **B. 平台级应用 + 用户 OAuth** | 我们申请一个飞书应用，用户只扫码授权 | 体验最好，2 步完成 | 需要飞书应用审核/上架；用户数据经平台应用 |
| **C. 混合** | 内测用 A，规模化切 B | 渐进、可回退 | 两套代码路径并存 |

**建议**：先按 A 服务少量真实用户跑反馈，同时启动 B 的申请（审核有周期）。代码层已按多租户设计（业务函数显式接收 `integrationId`），切 B 时不必重构。

## 七、落地阶段

### 阶段 1：MCP 服务层（服务器）
- 新增 `/api/mcp/*`（远程 HTTP MCP）+ 设备授权码
- 工具集：`doctor`（无副作用）/ `whoami` / `list_reports` / `get_report_summary` / `get_pipeline_status`
- 用户列表只返回**已生成的报告**，不开放原始逐字稿

### 阶段 2：宿主接入验证
- 豆包工作：新建自定义连接器（HTTP），填入 MCP URL
- WorkBuddy：`~/.workbuddy/mcp.json` 加一条 HTTP 连接器
- 验证：用户不点名工具也能查到自己的报告

### 阶段 3：推送链路核对
- 复用现有 `meeting_report_notification_tasks`（飞书卡片，含幂等键与租约）
- 若需同时推到宿主会话：用游标增量（见 [AI宿主接入设计.md](./AI宿主接入设计.md) 第八章）

### 阶段 4：上架
- 发 npm 包（`npx -y` 启动的 stdio 薄壳）
- 豆包工作 MCP 生态准入材料
- WorkBuddy 连接器市场

## 九、本设计推翻的早期假设

| 早期假设 | 修正 |
|---|---|
| 「会议结束靠宿主定时任务触发」 | ❌ 错。是**飞书妙记生成事件**驱动，不是定时 |
| 「宿主组件可以替代常驻服务」 | ❌ 错。妙记事件订阅是消费时注册、退出即注销 |
| 「豆包工作没有飞书能力」 | ❌ 错。它内置 `ConnectorVendor_Lark`，且沙箱里直接跑 `lark-cli` |

## 十、本地报告如何落到服务器（**待决策**）

### 问题

本地 MCP 用本机 lark-cli + 分析引擎跑出报告后，需要给用户一个**报告页链接**
（含四象限图、语义互动网络图、PDF 导出）。飞书云文档是纯文本，**复现不了这两张图**，
只能当兜底。所以报告必须落到服务器上，换一个 `report_public_id`。

### 代码级约束（实测确认）

```ts
// src/lib/db/schema.ts · meeting_records
userId: uuid('user_id').notNull(),
integrationId: uuid('integration_id').notNull(),
```

- 两个字段都是 **NOT NULL**
- 但 `integration_id` **没有外键约束**（整个 schema 只有一处 `.references()`，在 `feishu_project_org_targets.projectId` 上）

也就是说：技术上可以塞任意 uuid，但语义上"这份报告属于哪套飞书集成"会说不清。

### 三个选项

| 方案 | 做法 | 复用程度 | 代价 |
|---|---|---|---|
| **A. 绑定现有集成** | 报告挂到该用户已有的 `integrationId` 下 | ✅ **现有报告页零改动**（`/report/v2/{id}` 直接可用，含图表） | 要求用户先配好飞书集成；语义勉强（报告并非由这套集成产生） |
| **B. 新建 host 报告表** | 新表 `host_published_reports` + 新报告页 | 需新页面，但可复用 `PersistentReportView` 组件 | 不动现有表与线上数据；多一套存储与页面 |
| **C. 放宽 integration_id** | 改成可空 | ✅ 复用现有报告页 | 改现有表结构，影响面最大，且要审所有读该字段的查询 |

### 推荐：**B**

理由：
1. 不动现有表结构和线上数据——最保守
2. 报告页组件可直接复用（`PersistentReportView` 按 `analysisSchemaVersion` 自动分流）
3. 语义干净：`meeting_records` 表示"由飞书集成自动分析出的报告"，
   `host_published_reports` 表示"由宿主组件发布上来的报告"，两条来源不混

**若选 A**：内测最快，但每个用户必须先完成六步集成初始化才能用 MCP 发报告。

### 接口契约（已写入 teaming-mcp/README.md）

```
POST {TEAMING_SERVER_URL}/api/host/reports
Authorization: Bearer {TEAMING_HOST_TOKEN}
{
  meetingTitle, meetingStartedAt, feishuMeetingId,
  analysisResult,        // 完整 AnalysisResultV2
  transcript,            // 可空
  clientRequestId        // 幂等键
}
→ 200 { reportPublicId, reportUrl }
```

MCP 侧**已经实现**（`src/publish.mjs`），三级优先：
显式 URL → 服务器报告页 → 飞书文档兜底。服务器端待实现后即自动生效。
