## 3. 必须整改的问题

### F01 · P1：报告落库与交付登记不在同一事务，会永久漏交付

**证据：** `src/lib/feishu/pipeline/meetingPipelineProcessor.ts:1010` 先独立提交报告；`:1119`、`:1176` 随后登记 Base/通知任务，`:1138`、`:1194` 捕获异常后只记日志；`:1091` 仍完成主任务。下次入口在 `:654` 发现会议 completed 后直接返回，未补建缺失交付任务。

**触发与影响：** 报告保存后进程退出，或任一任务登记失败，数据库会存在已完成报告却没有对应交付需求。消费者只能处理已存在任务，因此重启不能自动补偿；用户仍收不到消息。

**整改要求：** 同一数据库事务提交报告、版本、接收人绑定、两类交付需求及主任务完成状态。Base 目标缺失可以登记 blocked，不应取消有效通知需求。仓储统一接收事务执行器。为本次发布后异常缺失的交付提供可审计修复入口；历史报告不应默认批量补发。

**理由：** 消除数据已经成功、后续工作却未登记的空窗，恢复交付时无需重新调用模型。

**复验：** B07。在报告更新后、两类任务登记之间分别注入错误/终止进程，结果必须全部提交或全部回滚；恢复后每种任务恰好一份，已保存分析不重跑。

### F02 · P1：Base 同步完成后租约已清空，新版本重排必然失败

**证据：** `src/lib/feishu/delivery/baseSyncProcessor.ts:312` 调用完成函数，`deliveryTaskStore.ts:174` 将状态改 succeeded 并清空 lease_token；随后 processor `:350` 检查新版本并在 `:352` 使用旧租约重排。`requeueDeliveryTask` 仍要求原 lease_token 匹配，更新不到该行；调用者没有检查返回值，却写入重排成功日志。

**触发与影响：** V1 执行中 V2 入队，requested_version 推进、running 保持；V1 完成后形成 succeeded、synced_version=V1、requested_version=V2。重排失败，没有后续事件时 V2 永久留在数据库，Base 落后。

**整改要求：** 在持有有效租约时，用一次原子状态更新同时确认已写版本并判断是否 pending；不要先释放租约再用旧租约操作。更新返回实际行数/结果，失去租约时不能记录成功。

**理由：** 版本合并只有最终版本一定能够交付才成立，否则会静默丢数据。

**复验：** B08。阻塞 V1 外部写入，推进 V2、V3，再释放 V1；必须自动写到 V3，最终 requested_version=synced_version，日志与真实状态一致。

### F03 · P1：任务快照没有固定实际 Base 目标，切换期次可能写错表

**证据：** `src/lib/feishu/delivery/baseSyncTaskStore.ts:72` 快照仅含 projectId、orgTargetId、orgName。processor `:284` 调用 `createOrgTargetBitableAccess`；`src/lib/feishu/bitable/bitableOpenApi.ts:89` 仍调用 `getGlobalBitableConfig()`，后者 `:70` 读取当前 active project 的 appToken/tableId。

**触发与影响：** 旧期任务排队后切换 active project，执行时业务项目仍是旧期，实际写入地址却来自新期。可能错表创建，也可能用旧 recordId 更新新表而失败。只验证 orgTarget.projectId 不能保证实际目标不变。

**整改要求：** 建任务时冻结实际 appToken、tableId、目标身份及版本；执行时只使用已确认目标。若不保存值，可使用不可变配置版本引用。无法确认目标则 blocked，不回退到当前活动项目。recordId 必须与目标表成对保存。

**理由：** 保护不同期次数据隔离，避免无报错的错误写入。

**复验：** B12。A 期任务排队后切换 B 期，再执行 A 期任务，验证请求的实际 appToken/tableId 与记录仍属于 A；B 表没有 A 的数据。

### F04 · P2：分阶段同步被改成仅终态同步，不符合已约定业务

**证据：** `src/lib/feishu/pipeline/meetingPipelineProcessor.ts:931` 明确写“中间态不写 Base”；建档和文字稿保存后未登记同步需求。当前 enqueueBaseSyncTask 调用仅位于最终失败及分析完成路径。`src/lib/reports/meetingReportStore.ts:244` 保存文字稿也没有推进 data_version。

**影响：** 分析长时间未结束时，运营者看不到已获得的基础信息和文字稿。这不是独立 worker 必然带来的限制，而是删除了原有业务行为。

**整改要求：** 建档、文字稿就绪、报告完成/最终失败，分别事务化推进版本和 Base 需求；积压时允许合并最新快照。保持“处理状态字段仅展示终态”的约定，但不能因此停止中间阶段的其他字段同步。

**理由：** 保留运营者的过程可见性，同时通过合并减少 API 请求，不必为每个阶段新增表。

**复验：** B02、B04。刻意延迟分析，Base 同一记录应先看到基础信息，再看到文字稿，最后出现结果；中间写入失败不阻断分析与通知。

### F05 · P2：初始化尝试登记太晚，创建应用阶段失败仍不可见

**证据：** `src/lib/feishu/integration/integrationSetup.ts:270` 必须先取得 integration，`:287` 才 startOrTouchSetupAttempt；整个源码中没有在创建应用入口调用该登记函数。虽然表允许 integration_id 为空，StartOrTouchInput 仍要求 integrationId。服务器另造 setupTraceId，没有接入前端已有请求链路 trace。

**影响：** 用户点击创建后、integration 产生前失败，运营表仍找不到这次尝试，最初要解决的“新增用户卡在哪一步”只解决了后半程。

**整改要求：** 创建流程发起时登记 attempt，暂时未知的身份字段允许为空或使用安全会话关联；成功后补关联 integration/user，沿用同一 trace。创建失败、超时、中断也必须有可查终态。

**理由：** 最容易流失的前期用户必须纳入观测，不能用“没有集成记录”推断没人尝试。

**复验：** A01、A05。故意让创建应用在 integration 生成前失败，管理视图仍显示尝试、阶段、原因和下一步；刷新页面能关联同一次尝试。

### F06 · P2：轮询会重置进度时间，state_version 没有防止旧结果覆盖

**证据：** `src/lib/feishu/integration/setupAttemptStore.ts:71` 每次 touch 都重置 currentStep、stepStartedAt、lastProgressAt 并增加版本；检查入口固定传 create_app。resolve 根据 integrationId 找当前活跃 attempt，更新只按 id，没有携带该次检查的 attempt ID/预期版本。

**触发与影响：** 没有实际进展的轮询会让“卡住多久”归零；旧检查迟到且期间已经开始新 attempt 时，可能把旧结果写到新尝试。单纯递增 state_version 不提供并发保护。

**整改要求：** 分开记录观察/心跳时间与实际步骤推进时间；检查开始返回 attempt ID 和版本，完成时用对应 ID+版本条件更新，忽略过期结果。是否新增字段由实现决定，关键是语义和条件更新正确。

**理由：** 运维看到的应是真实进展，避免误判卡顿及错误状态回退。

**复验：** A06。同一状态轮询十次不改变 last_progress_at；延迟旧检查结果到新一轮开始后返回，不允许污染新 attempt。

### F07 · P2：初始化人数将“历史未采集”算成 0，缺少当前可用口径

**证据：** 新汇总视图只以 first_initialized_at 非空统计完成数，见 `supabase/migrations/20260920100000_ops_view_enhancements.sql:15`。实时查询第四期：绑定用户 2；两条集成 status=success 且 initialized_at 非空；first_initialized_at 均为空，所以汇总 initialized_user_total=0。视图也没有单独输出当前可用人数及状态新鲜度。

**影响：** “新字段尚无历史证据”被展示为“没人完成初始化”，用户仍不能据此获得可信的完成名单。数据库 success 也不足以证明现在实时可用。

**整改要求：** 分开已确认首次完成、历史完成有证据但首次时间未知、当前可用及观察过期/未知口径。使用历史 initialized_at/审计作为明确标注的历史证据，不能填造首次完成时间。完成名单与人数使用同一去重及项目范围。保留替代/软删除集成的历史完成追溯能力。

**理由：** 解决用户实际想问的人数与姓名问题，不为新字段填满而制造假事实。

**复验：** A02、A03、A04、A08。当前这两条记录不能仅因 first_initialized_at 为空被解释为“未初始化”；授权后来失效时，历史完成仍在、当前可用单独变化。

### F08 · P2：字段改名后修复类型，映射仍丢失

**证据：** `src/lib/feishu/bitable/fieldBinding.ts:178` 仅在旧状态为 bound 时跟随 fieldId；type_mismatch 状态会重新按约定名称找字段。

本轮直接执行该文件的实际 reconcile 函数：原会议分类字段 ID=fld_test；改名为“新分类名称”并改为 select，得到 type_mismatch，ID 仍在；把同一个 ID 的类型恢复 text 后，再对账得到 unbound、fieldId=null。这个结果已隔离复现，非假设。

**整改要求：** 非 disabled 且已有 fieldId 时优先按 ID 查找，不因暂时类型不匹配丢掉绑定；同一个 ID 恢复兼容类型后应回到 bound。字段 ID 真消失时的重绑需明确规则，不混同简单改名。

**理由：** 运营者修复错误后应能恢复同步，不该被迫把展示名称改回代码默认中文名。

**复验：** B13 补充：改名 → 改错类型 → 恢复类型，ID 始终不变；最终自动恢复分类写入，且不会绑定到另一个同名字段。

## 4. 字段名称硬编码的准确结论

不能说“已完全没有字段名称硬编码”，也不应把所有中文字符串都当作 bug。

- `BASE_BUSINESS_FIELD_SPECS` 集中维护默认名和别名，用于初次发现字段，是合理的兼容配置。
- `bitableSync.ts:84` 直接镜像 analysis_result.metadata.meetingType，未强行压缩为旧分类枚举，这部分符合要求。
- 主同步查询显式传入解析后的会议 ID 字段名，写入经过绑定解析，这部分方向正确。
- `bitableOpenApi.ts:225` 的 toRecord 仍固定读取“会议ID”“处理状态”“会议文字稿”“报告链接”等；无项目上下文时，绑定服务也回退默认名称。应在文档中披露剩余范围。
- 当前新交付主路径主要取查询返回的 recordId，因此尚不能据上述读取硬编码断言本次主路径一定失败。执行 AI 应补充调用覆盖检查：仍需这些字段值的有效入口接入绑定；无调用的旧兼容代码可以另行清理，不强制为此大重构。
