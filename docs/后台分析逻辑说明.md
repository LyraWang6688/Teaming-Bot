## 1. 系统概述与版本路由

本系统基于 **Amy Edmondson Teaming 框架** + **David Kantor 互动功能模型**，对会议文字稿进行结构化分析。当前项目中，网页上传任务和飞书会议自动分析都复用同一套 V2 分析内核。

### 1.1 V1 / V2 并存设计

为支持历史报告的稳定回放，分析与渲染层都按 `analysisSchemaVersion` 字段路由：

| 版本 | schemaVersion | 分析引擎 | 渲染器 | 类型定义 |
|------|---------------|---------|--------|---------|
| V1（冻结） | 1 | 已下线，旧报告不再重新分析 | `AnalysisDashboardV1` | `src/types/v1.ts` |
| V2（活跃） | 2 | `src/lib/analysis/engine.ts` | `AnalysisDashboardV2` | `src/types/v2.ts` |

`src/lib/reports/meetingReportStore.ts` 中的 `MEETING_REPORT_SCHEMA_VERSION` 已从 1 升到 2。所有新写入的报告都打上 `schemaVersion=2` 标记。

### 1.2 当前核心文件

| 文件 | 作用 |
|------|------|
| `src/services/analysisService.ts` | 分析入口（极简包装，委托 engine） |
| `src/lib/analysis/engine.ts` | 两阶段编排（证据 + 报告并行） |
| `src/lib/analysis/transcript.ts` | 飞书妙记转写解析与发言占比计算 |
| `src/lib/analysis/prompts.ts` | 证据系统提示词与报告系统提示词 |
| `src/lib/analysis/evidence.ts` | 证据引用归一化与可回溯校验 |
| `src/lib/analysis/evidenceBudget.ts` | 输出 token 预算自适应 |
| `src/lib/analysis/decision.ts` | Zone / 相邻区域 / position hint 推导 |
| `src/lib/analysis/provider.ts` | 模型调用（外部火山方舟端点） |

### 1.3 核心设计原则

- 证据一次提取，写作并行：正常路径 3 次模型调用（证据 1 + 报告主体 1 + Part 4 领导建议 1）。
- 代码确定事实，模型只做语义判断：发言者识别、占比、姓名对齐、合并语义互动频次都由 `transcript.ts` / `evidence.ts` 处理。
- 证据必须可回溯到原文，不可回溯的证据降级或舍弃。
- V1 / V2 渲染器互不影响，旧报告继续按生成时的模板渲染。

## 2. 分析流程总览

```text
会议文字稿
  │
  ├─ 入口1：网页上传异步任务
  │   ├─ POST /api/analyze/tasks 创建 web_analysis_tasks
  │   ├─ 后台任务解析文件 / 提取文字
  │   └─ 调用 analyzeMeetingText()
  │
  ├─ 入口2：飞书会议流水线
  │   ├─ 妙记转写导出
  │   └─ 调用 analyzeMeetingText()
  │
  └─ analyzeMeetingText()  →  analyzeTranscript()
      ├─ transcript.ts 解析转写：发言者、轮次、占比、会议时长
      ├─ 第一阶段：invokeJson(evidenceRequest)
      │   ├─ 提取会议性质 / 核心张力
      │   ├─ 提取心理安全、高要求与问责、学习过程证据
      │   ├─ 提取互动功能事件与语义互动
      │   └─ 完成 Zone / 相邻区域 / 维度方向 / 参与者类型锁定
      ├─ 代码锁定 lockedDecision
      ├─ 第二阶段（并行）：
      │   ├─ invokeJson(reportRequest)        # 主体报告
      │   └─ invokeJson(leaderAdviceRequest)  # Part 4 领导建议
      ├─ 引用校验 + 必要降级
      ├─ 名称对齐 + 语义互动合并
      └─ 返回 AnalysisResultV2（schemaVersion=2）
```

### 2.1 关键说明

- 证据阶段失败时，第二阶段两个写作调用直接跳过，立即生成基础事实版（保守报告）。
- 证据阶段成功后，主体报告与 Part 4 领导建议并行写作，二者使用同一份 evidence + lockedDecision。
- 报告写作阶段不得重新分类、重新判断区域，也不得修改锁定字段。

## 3. 第一阶段：证据包提取

模型在第一阶段只提取可观察事实并完成唯一一次理论判定。证据系统提示词见 `src/lib/analysis/prompts.ts` 的 `EVIDENCE_SYSTEM_PROMPT`。

### 3.1 证据包必须包含

- 会议性质、目标和核心张力；
- 四类团队学习过程的可观察行为；
- 心理安全的人际风险表达及其后续回应；
- 高要求与问责的来源、目标、标准、期限、验收、追踪、后果，以及这些要求如何被承载；
- 每位发言者在本次会议中的互动功能证据；
- 有方向的语义互动；
- 候选未完形、非共识和领导行动杠杆。

### 3.2 心理安全证据规则

- 禁止从沉默、发言少、会议严肃、没有冲突或全员赞同直接推断心理安全。
- 区分内部成员、外部客户/用户/专家、主持或助教和身份不明者。
- 心理安全证据拆成内部互动与跨边界互动，客户敢于反馈不能单独证明内部团队心理安全。
- 心理安全较低不以公开羞辱为必要条件；当至少两类可回溯的限制事件形成组合时，可将原本犹豫的 insufficient 谨慎锁为 lower，但不得仅凭沉默定性。

### 3.3 高要求与问责证据规则

- 拆成要求来源、目标/期限、标准/依据、验收/验证、追踪/后果，以及共同拥有/闭环等质地。
- 判为 higher 时必须有至少一个可回溯的实质要求信号。
- 高要求采用双路径校准：
  - 心理安全较低或不足时，外部清晰高标准、紧迫期限、验收或后果可以在没有共同拥有的情况下保持 higher，以保留焦虑区；
  - 心理安全较高时，准备进入学习区必须同时具备"可判断结果质量的明确标准"与"已承诺的试验/验收/客户反馈，或发现偏差后的纠偏回路"。
- 心理安全较高且存在推进压力、但尚未同时形成上述"标准锚点+执行机制"时，代码将 accountability 校准为 lower，并可保留"舒适区，靠近学习区边界"。
- 共同拥有、主动承担、验证与闭环用于描述要求如何被承载，不再作为 higher 的硬门槛。
- 核心产出未解决或尚无验证承诺也不再被代码强制降级，因为它可能出现在"外部高要求 + 低心理安全"的焦虑区。

### 3.4 证据阶段附加要求

- 标记 `standardStrength / validationMode / monitoringMode`，并用原话一致性校验拦截三种常见混淆：
  - "先做一个功能"是范围而非质量标准；
  - "去问老师/客户怎么做"是信息请求而非验证；
  - "明天再看回复"是普通跟进而非纠偏机制。
- 先列出成员的功能事件，再由代码按事件数量确定主要功能。
- 同一 source→target 的多条语义互动由代码合并，频次相加并据此确定线宽。
- source 和 target 每个字段只允许一位发言者；若模型仍输出"A→B、C"，代码仅在 B、C 都能唯一对齐发言者时拆成两条边。
- 姓名首先对齐飞书转写中的标准名。别名必须有可在转写中逐字回溯的对应证据；冲突、歧义或无证据别名不自动合并。
- 心理安全、高要求与问责、学习过程、互动功能和 Part 3 候选项中的引用，都必须能在原转写中回溯。
- 明确哪个维度确实接近高低边界，不能用"方向失焦"等会议问题替代相邻区域。

## 4. 核心概念：Zone 计算

模型分别判断两个维度的方向：

- `higher`
- `lower`
- `insufficient`

代码组合（见 `src/lib/analysis/decision.ts` 的 `deriveZone`）：

| 心理安全 | 高要求与问责 | Zone |
|---|---|---|
| higher | higher | Learning |
| higher | lower | Comfort |
| lower | higher | Anxiety |
| lower | lower | Apathy |
| insufficient | insufficient | Difficult to Judge |
| insufficient | higher/lower | 可能是纵向相邻的两个区域 |
| higher/lower | insufficient | 可能是横向相邻的两个区域 |

前台坐标按 Edmondson《Teaming》第四章 Figure 4.1 固定：

- 横轴为高要求与问责，左低右高；
- 纵轴为心理安全，下低上高；
- 左上舒适区、右上学习区、左下冷漠区、右下焦虑区。

### 4.1 锁定字段

第一阶段完成后，`lockedDecision` 包含：

- 区域（zone）
- 相邻区域（adjacentZone）
- 维度方向（boundaryDimension）
- 参与者类型（participantType）
- 主要互动功能（primaryInteractionFunction）
- 语义互动（semanticInteractions）
- 跨边界状态（crossBoundaryState）

第二阶段写作不得修改任何锁定字段。

## 5. 第二阶段：报告写作

模型只根据证据包和 lockedDecision 撰写四部分报告。lockedDecision 中的区域、相邻区域、维度方向、参与者类型、主要功能、语义互动和跨边界状态均不可修改。提示词要求先找到本场会议独有的核心张力，禁止套话、机械追加"也曾发挥"以及机械化领导建议。

### 5.1 Part 3 两套互斥结构

- `unfinishedDialogues` 表示对话完成状态，字段为 `topic / conversationSoFar / whatRemains`；
- `unseenDisagreements` 表示可观察的认知差异，字段为 `topic / differentConcerns / sharedGoal / whyItMatters`；
- 一个人提出挑战但无人回应时只能进入未完形；非共识必须能回溯到至少两种不同关注；同一主题不得在两栏重复。

### 5.2 旧报告字段兼容映射

导入旧报告时：

- `whyUnfinished / whyNeedsClosure / whatEachSideSays` 会分别兼容映射到 V2 字段 `conversationSoFar / whatRemains / differentConcerns`；
- 前台只呈现新结构。

## 6. 质量门与引用校验

第二阶段结果必须满足：

- 每位代码识别出的实质发言者都出现在成员节点中；
- 不得生成不存在的发言者；
- 第一阶段判为 higher 的高要求与问责必须包含目标、标准、期限、验收、追踪或后果中的至少一类可回溯证据；外部施加的明确高标准无需以共同拥有为前提；
- 第一阶段主要功能必须有对应功能事件，语义互动必须有原文证据；
- 引用校验会统一字形、空白和标点后回到原转写，不接受仅有概括而没有原话的"证据"；
- 无法安全对齐的单条互动或别名会触发一次证据包重做；仍失败时舍弃该边，不让一条不可靠连线拖垮整份报告；
- 其他引用重做后仍不可回溯时，删除该证据：
  - 心理安全或高要求的 higher 判断因此失去必要证据时降为 insufficient；
  - 成员没有留下可回溯功能事件时降为 silent；
  - 未完形、非共识或学习过程候选项则直接舍弃。
- 第二阶段不得改写锁定区域、标签或成员主要功能；
- 前台文字不得暴露 accountability、higher 等后台字段名；
- 跨边界会议必须呈现跨边界学习；
- Part 1 必须直接使用规范的"主区域，靠近相邻区域边界"表达；
- Part 1、Part 2 和成员观察达到适度信息量，但不以堆字数替代语义校验；
- Part 3 的未完形必须同时有"走到哪里"和"还缺什么"；非共识必须有可观察的不同关注，前台结构同时保留共同目标；
- 领导建议默认为一条，最多两条；
- 建议不得使用已知机械起手式；
- JSON 失败时先做本地标点修复，再做一次只处理语法、不重新分析会议的模型修复；只有内容被截断或局部修复仍失败时，才允许整体重写一次；
- **报告必达**：对已识别出至少两位实质发言者的有效输入，模型超时、JSON 损坏、引用或编辑校验失败都不得最终变成失败卡片。系统依次采用安全 JSON 修复、JSON 语法局部修复、扩大输出预算后的完整重写、保留较好候选并补齐缺失字段，最后使用保守报告；
- 两个维度都缺少信号时暂不定位；只有一个维度缺少信号时呈现两个可能区域，不能编造引文或强行把不确定维度写成确定方向；
- 只有文件无法解析、文本过短或未识别到至少两位实质发言者时，才可以阻止生成，并提示用户修正输入。
- 批量上传按单并发逐份处理，以生成稳定性优先，避免两份长上下文请求相互放大超时和截断风险。

## 7. 相邻区域与标签

第一阶段默认 `boundary.dimension=none`。两个维度都有明确方向时，只有同一维度同时存在可回溯、力量接近的正反证据，代码才接受"靠近边界"的判断。

- 仅一个维度为 `insufficient` 时不属于"靠近边界"，而属于区域不确定：代码直接把点放在该维度分界线上，并呈现"可能是 X 区或 Y 区"。
- 只有两个维度都为 `insufficient` 时才暂不定位。

### 7.1 明确方向下的相邻区域映射

- 学习区接近 accountability 分界 → 舒适区；
- 学习区接近 psychologicalSafety 分界 → 焦虑区；
- 舒适区接近 accountability 分界 → 学习区；
- 焦虑区接近 psychologicalSafety 分界 → 学习区；
- 其他区域按同样的共边关系计算。

### 7.2 前台标签规范

三类规范表达：

- "学习区"等明确区域；
- "学习区，靠近舒适区边界"等明确主区域下的边界倾向；
- "可能是舒适区或学习区"等单维度证据不足的两区判断。

会议的具体限制另写在解释正文，不得替代相邻区域标签。

## 8. 模型参数与 JSON 容错

### 8.1 模型参数

- 证据提取：temperature 0.05；
- 报告综合：首次 0.40，编辑修订 0.20；
- 三个任务均要求 JSON object；
- 默认超时 480 秒，可由 `LLM_TIMEOUT_MS` 调整。

### 8.2 外部端点配置

- 配置 `LLM_API_KEY + LLM_BASE_URL` 时，外部火山方舟请求直接走 OpenAI 兼容的 `/chat/completions` 接口，实际发送 `response_format={type:"json_object"}`、`max_tokens` 与 thinking 配置，并记录 `finish_reason` 和 token 用量。
- `ANALYSIS_MODEL` 使用方舟 Endpoint ID。
- 为兼容历史部署，`provider.ts` 的 env 读取采用 fallback chain：
  - API Key：`LLM_API_KEY || DOUBAO_API_KEY || ARK_API_KEY`
  - Base URL：`LLM_BASE_URL || DOUBAO_BASE_URL || ARK_BASE_URL`
  - Model：`ANALYSIS_MODEL || DOUBAO_MODEL || 'doubao-seed-2-0-pro-260215'`
- 未配置外部方舟端点时，`invokeProvider` 直接抛 `ModelRequestError`（不可重试），不再回退到任何内置 SDK。
- Coze SDK 依赖已移除，当前项目不再依赖 `coze-coding-dev-sdk` 包。

### 8.3 JSON 容错与诊断

- 记录每次调用的 `finish_reason`、内容长度、token 用量以及结构化输出/长度约束是否真正生效；
- 对缺失逗号和尾随逗号先做本地、内容不变的安全修复；
- 正常结束但仍有语法错误时，只把已有 JSON 交给低温语法修复，不重新读取会议和重新判断；
- `finish_reason=length` 表示内容被截断，不能伪装修好：完整重写时输出预算扩大 35%，上限为 12000 tokens；
- 局部修复与扩大预算后的重写仍失败时，才进入保守报告。

### 8.4 证据输出预算

`src/lib/analysis/evidenceBudget.ts` 提供两档预算：

- `STANDARD_EVIDENCE_MAX_TOKENS = 6000`
- `EXTENDED_EVIDENCE_MAX_TOKENS = 8500`

按证据阶段失败次数自适应升级。

## 9. 代码确定的事实（transcript 解析）

`src/lib/analysis/transcript.ts` 负责：

- 识别飞书常见"姓名 + 时间戳"格式；
- 合并同一发言轮次的多行文本；
- 计算每位发言者转写字符数、轮次和占比；
- 将占比稳定地四舍五入到合计 100%；
- 排除只含语气词、身份未知的通用 Speaker 标签；
- 识别会议时长和输入质量提醒。

发言者识别、占比、姓名对齐、合并语义互动频次都由代码确定，模型不得参与。

## 10. 降级与保守报告

### 10.1 触发条件

- 证据阶段最终不可用；
- 报告写作多次重试后仍无法生成可用 JSON；
- 引用校验失败且无法局部修复。

### 10.2 降级路径

1. 安全 JSON 修复（本地标点修复）；
2. JSON 语法局部修复（低温模型只修语法）；
3. 扩大输出预算后的完整重写；
4. 保留较好候选并补齐缺失字段；
5. 保守报告（基础事实版）。

降级报告必须标注证据局限：

- 两个维度都缺少信号时暂不定位；
- 只有一个维度缺少信号时呈现两个可能区域；
- 不能编造引文或强行把不确定维度写成确定方向。

### 10.3 阻止生成的条件

只有以下情况才允许阻止生成报告：

- 文件无法解析；
- 文本过短；
- 未识别到至少两位实质发言者。

此时提示用户修正输入。

## 11. 后端入口与任务链路

### 11.1 统一分析入口

- `src/services/analysisService.ts`：统一分析入口，极简包装 `engine.analyzeTranscript`。
- `src/lib/analysis/engine.ts`：V2 分析引擎。

### 11.2 网页上传链路

- `src/app/api/analyze/tasks/route.ts`：创建异步任务；
- `src/app/api/analyze/tasks/[taskId]/route.ts`：轮询状态；
- `src/lib/analysis/inputParser.ts`：解析 `.txt` / `.docx`；
- `src/lib/analysis/webAnalysisTaskProcessor.ts`：后台执行分析。

### 11.3 飞书会议链路

飞书链路不修改分析内核，只负责把转写文字交给 `analyzeMeetingText()`。自动化外壳与分析引擎保持解耦。

飞书报告通过 `analysisSchemaVersion` 字段路由：

- `schemaVersion=1` → V1 渲染器（旧报告冻结）；
- `schemaVersion=2` → V2 渲染器（新报告）；
- 缺省值视为 1，保证向前兼容。

### 11.4 持久化字段

`meeting_records.analysis_result` 存储完整 V2 JSON，`meeting_records.analysis_schema_version` 标记版本号，供 `PersistentReportView` 路由到对应渲染器。

### 11.5 `web_analysis_tasks`

该表用于承接网页上传异步分析任务，避免浏览器请求长时间挂起。关键字段包括：

- `id`
- `status`
- `meeting_text`
- `result`
- `attempt_count`
- `last_error_type`
- `last_error_message`
- `started_at`
- `completed_at`
