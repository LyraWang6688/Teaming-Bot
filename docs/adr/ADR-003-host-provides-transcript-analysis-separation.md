# ADR-003: 取数与分析分离——宿主提供逐字稿，MCP 只做分析

- **状态**：Accepted
- **日期**：2026-10-14
- **类别**：架构边界 / 多租户接入
- **取代**：无（与 ADR-002 并存；本文修正 ADR-002 关于"事件源不可下沉"在**豆包账号**场景下的可行性判断）

---

## Context

2026-10-14 用真实账号做了一组对照实验，得到三条硬事实。它们共同推翻了"每个用户在自己企业里建一个飞书应用"这个前提。

### 事实一：豆包账号在飞书侧被彻底限制

两条路都实测堵死：

| 路径 | 做法 | 结果 |
|---|---|---|
| A | 为豆包账号**创建**新应用（网页初始化向导） | 应用创建成功，但 `applicationConfig.patch` 立刻失败：`21001 Access denied by access control policy` |
| B | 豆包账号**授权一个已存在**的应用 | 授权页直接拒绝：「你没有"…"的使用权限」 |

`[Repo]` 路径 B 的对照实验最干净——同一个应用 `cli_aa1c820068f85cb6`：

```
王颖（普通飞书账号）    → ✅ 能授权，且整条链路跑通
豆包账号               → ❌ 你没有该应用的使用权限
```

唯一变量是账号类型，排除了"应用配置不同""时间点不同""代码有 bug"。

路径 A 的对照同样干净——同一天、同一套代码：

```
郭奕彤（普通账号，16:32 建）  → ✅ 应用可用，拿到 publishedVersionId
豆包账号（20:13 建）          → ❌ 21001
```

### 事实二：宿主自带的飞书能力**对豆包账号是通的**

`[Host]` 豆包工作执行飞书命令时，用的是**它自己的内部应用**，不是用户的：

```json
{ "ok": true, "identity": "user",
  "context": { "app_id": "1044603",                       // 数字 ID，宿主内部应用
               "user_open_id": "ou_90bf…a7eee" } }        // 宿主侧的飞书身份
```

`ok: true` —— **没有权限错误**。返回空列表只是因为那个身份下确实没有会议数据。

### 事实三：宿主具备触发与调度能力

`[Host]` 豆包工作可创建定时任务，且任务内能直接调用它内置的 `lark-cli`。
实测已建立一个每小时执行的妙记监控任务并成功生效。

### 由此暴露的核心矛盾

```
产品要在用户开会后自动给出分析报告
        ↓
必须有【事件源】+【能读到该用户会议的身份】
        ↓
"每用户建应用"这条路：豆包账号走不通
```

而 MCP 本身**不能监听事件**——工具只在被 agent 调用时执行，没有常驻进程。

---

## Options Considered

### Option A：维持现状——每用户建应用

- 优点：已是 ADR-002 的实现形态，报告页、多维表格写入全都在服务器侧跑通。
- 否决：**豆包账号整类用户不可用**。对照组已证明这是账号类型层面的限制，配置无法绕过。

### Option B：改用商店应用（ISV）

- 优点：跨租户设计，理论上覆盖面最广。
- 否决（暂缓）：**未验证**豆包账号能否安装/授权商店应用；且应用形态、审核与分发成本都远高于当前阶段需要。**保留为事实二、三都失效时的兜底。**

### Option C：取数与分析分离——宿主取数，MCP 只分析 ★选中

- 宿主用**它自己的**飞书能力读取该用户的会议与妙记，取出逐字稿；
- 逐字稿交给 MCP，MCP **完全不接触飞书**，只跑分析；
- 服务器负责报告落库、公开报告页、多维表格写入（平台应用身份，已有）；
- 推送与汇报由宿主用它的飞书能力完成。

### Option D：换通道，不依赖飞书授权

- 例如网页上传会议记录。
- 否决：丢掉"用户什么都不用做"的核心产品形态。

---

## Decision

**采用 Option C。** 明确边界：

| 能力 | 归属 | 理由 |
|---|---|---|
| 读妙记 / 会议 | **宿主** | 它有内置飞书应用，豆包账号可用（事实二） |
| LLM 分析 | **MCP** | 不碰飞书 → 不需要任何飞书授权；模型与算力集中在服务器侧可控 |
| 触发 | **宿主定时任务** | MCP 不能监听事件（无常驻进程） |
| 推送 / 汇报 | **宿主** | 它有飞书能力；服务器推送需要用户授权，豆包账号拿不到 |
| 写多维表格 | **服务器** | 走平台应用身份（`callGlobalBaseAppTenantOpenApi`），与用户授权无关 |
| 公开报告页 | **服务器** | `/report/v2/{publicId}` 已存在且可达 |
| 数据归集 | **服务器** | Supabase 多租户 |

**MCP 的对外契约据此收敛为一个核心工具**：

```
teaming_analyze_transcript(transcript, title?, meeting_id?) → job_id → 报告
```

**以豆包工作为第一个目标宿主推进。**

---

## Why

1. **绕开了唯一卡住整类用户的限制。** 事实一说明"授权我们的应用"死路一条；Option C 让 MCP 根本不需要授权。
2. **MCP 因此变薄，分发变简单。** 不再需要本机 lark-cli 授权、本机分析引擎配置、本机报告存储——今天踩过的那些坑（GUI PATH 找不到 lark-cli、端点缺失导致降级）大部分消失。
3. **现有资产全部可复用。** 分析引擎、报告页组件、多维表格写入、Supabase 归集都不用重做。
4. **模型可替换性保留在服务器侧。** 宿主不参与模型选择。

---

## Consequences

### Positive

- **豆包账号可用**：这是本次决策的直接收益，也是它唯一的硬理由。
- MCP 的分发形态退化为"一个不需要凭证的纯分析服务"。
- 触发器与数据源都留在宿主，随宿主能力升级自动受益。

### Trade-offs

- **依赖宿主能力。** 事实二、三都是 `[Host]` 证据，随宿主版本可能变化；且**豆包工作有内置应用，WorkBuddy 没有**（后者仍走用户自己的 lark-cli），所以两个宿主的行为不一致，不能假设一套配置通用。
- **身份绑定变复杂。** 服务器收到报告时无法自行验证"这份报告属于谁"——本机可以伪造上传者标识。产品化前需要独立的绑定机制。
- **报告链接暂缺。** MCP 侧 `publish.mjs` 会 `POST {TEAMING_SERVER_URL}/api/host/reports`，但**两端路径不一致且服务端未实现**，所以卡片目前只能落到飞书文档兜底页，图表出不来。

### Future Constraints

- 新增 MCP 工具时，**默认不得依赖飞书授权**；需要飞书能力的场景应经由宿主。
- 服务器新增宿主 API 时，路径统一走 `/api/host/v1/*`（与 `publish.mjs` 现有路径不一致，需对齐）。
- 报告归属的绑定机制落地前，服务器侧数据只能视为"不可信来源"，不得用于计费或权限判断。

## Evidence

`[Repo]` **豆包账号授权现有应用被拒**（授权页原文）：

```
你没有"王颖的飞书 CLI"的使用权限
当前登录账号为 Lyra Wang（豆包账号），你可选择以下已登录账号进行授权
  → 飞书个人用户 Lyra Wang   [选择]
```

`[Repo]` **同应用对照**（`app_access_token`）：

```
王颖（普通账号）  → ✅ ok
豆包账号          → ❌ 21001 Access denied by access control policy
```

`[Repo]` **同日建应用对照**：

```
郭奕彤 16:32 build → ✅ 可用
豆包账号 20:13 build → ❌ 21001
```

`[Host]` **宿主内置飞书应用**（豆包工作 task output 原文）：

```json
{ "ok": true, "identity": "user",
  "context": { "app_id": "1044603", "user_open_id": "ou_90bf0adc4303396438935662b26a7eee" } }
```

`[Repo]` **MCP 新工具端到端验证**（2026-10-14，teaming-mcp `9dba36d`）：

```
teaming_analyze_transcript(真实妙记逐字稿，282 行)
  → 立即返回 job_id
  → 60 秒后 done
  → 报告落盘，区域定位"可能是冷漠区或舒适区"
  → 全程无飞书调用
```
