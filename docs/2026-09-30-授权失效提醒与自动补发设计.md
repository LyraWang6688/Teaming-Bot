# 授权失效提醒与自动补发设计（方案 B）

> 日期：2026-09-30。状态：已实现（代码与隔离测试完成），待部署后真实链路验证。
> 决策记录：见 `PROJECT.md` 2026-09-30 条目。明确不做方案 A（到期前预防式扫描提醒）。

## 1. 背景与问题

飞书用户授权的 refresh_token 有效期为 7 天，仅在"有活动"（处理会议、服务器重启校验、配置页跑检查）时续期。连续 7 天无活动的用户授权静默失效（生产实证：2026-09-30 部署后王颖两个集成掉线，`feishu_authorizations` 显示 refresh_token 恰于部署前 17 小时过期）。

**当前链路的实际行为**（代码核实）：

1. 妙记事件到达 → `evaluateMeetingEligibility` 第一步 `fetchMeetingDetails` 使用用户 token → 抛出 `FeishuAuthorizationError`
2. 该异常未被资格检查捕获，冒泡到 `meetingPipelineProcessor` 通用 catch：按"临时错误"重试最多 3 次（每次都必然失败），最终任务 `failed`、`meeting_records` `failed`
3. 用户全程无感知：没有通知，报告静默不到达
4. 恢复只能管理员手动 SQL（`docs/2026-09-22-妙记所有者任务链路验收.md` 的事务恢复流程），无前端入口

**目标用户场景**：第四期为阶段性项目，用户开会频率不均，"7 天不开会"是常态而非异常，此问题必然高频出现。

## 2. 目标

- 授权失效导致会议无法分析时，**当场**用集成应用机器人私信告知用户"发生了什么、影响了哪场会、怎么修"
- 用户 90 天内（飞书会议详情接口官方时效）完成重新授权后，**系统自动**将因授权失效 blocked 的任务重新入队并补发报告，全程无需管理员介入
- 项目 archived 后停止一切此类提醒

## 3. 总体流程

```text
妙记事件 → 资格检查读会议详情 → 发现授权失效
  → 任务标记 blocked（gate.reasonCode=oauth_*，不重试、不建 meeting_record）
  → 发送重新授权提醒（同一失效周期内只发一次）
  → 用户点击提醒中的链接 → 免会话重新授权（飞书 OAuth 本人校验）
  → 授权成功回调：自动将该集成所有 oauth_* blocked 任务重新入队（90 天窗口内）
  → Worker 正常处理：导出妙记 → 分析 → Base 回写 → 推送报告
```

## 4. 详细设计

### 4.1 失败检测与状态落地

- 在 `evaluateMeetingEligibility` 中显式捕获 `fetchMeetingDetails` / `fetchMinuteInfo` 抛出的 `FeishuAuthorizationError`，返回：
  `{ allowed: false, status: 'blocked', reasonCode: `oauth_${error.code}` }`（如 `oauth_refresh_token_expired`、`oauth_refresh_failed`、`oauth_not_authorized`）
- 复用现有 gate 落地路径：任务 `blocked` + `payload.gate` 记录 reasonCode/message/checkedAt；不创建 `meeting_records`；**不重试**（授权失效在用户行动前必然持续失败，重试纯属浪费模型与 API 调用）
- `MeetingPipelineTaskPayload.skippedReason` 联合类型需补充 `oauth_*` 系列值（或调整类型定义允许 gate.reasonCode 自由文本，二选一，实现时以最小改动为准）

### 4.2 当场提醒（新建 reauthorizationReminderService）

- 触发：任务因 `oauth_*` 进入 blocked 时
- 通道：复用 `createFeishuSdkClient(integration)` + `im.message.create`（应用凭证 tenant_access_token，与用户 token 失效无关），接收人为该集成 `authorizedOpenId`
- 幂等去重：同一"失效周期"只提醒一次。判定依据：`feishu_integration_checks.details` jsonb 中记录 `reauthReminderSentAt`；授权恢复后清除。发送失败不阻断管线，记监控日志
- 项目截止：仅当关联 `feishu_projects.status = 'active'` 时发送；archived 项目静默
- 文案（已与本人确认）：

```text
【会议分析授权已过期】

你在 {事件日期} 有一场会议已结束，但未能生成分析报告。
原因：你的飞书授权已过期（连续 7 天未使用会自动失效）。
点击链接重新授权（只需几秒钟）：{reauthUrl}
授权成功后，系统会自动补发这场会议的分析报告。
请在 90 天内完成授权，逾期将无法补发。
```

- 文案约束：授权失效时 `fetchMeetingDetails` 即失败，**无法得知会议标题**，故文案只使用事件日期（`payload.telemetry.eventReceivedAt`），不写会议名；同一失效周期多场会议可合并为一条

### 4.3 免会话重新授权入口（关键设计点）

目标用户 7 天无活动，其 30 天登录会话也可能已过期；现有 `authorize/start` 要求会话且会话用户须拥有该集成，会话过期用户会走进"新用户向导 → OAuth 回调撞'该飞书账号已绑定到其他本地用户'"的死路。因此必须提供**不依赖既有会话**的重新授权链路：

- 提醒消息中的链接：`{PROJECT_PUBLIC_URL}/api/feishu/reauth/start?t=<签名令牌>`
- 签名令牌内容：`integrationId + 过期时间（如 7 天）`，用 `APP_ENCRYPTION_KEY` 派生密钥签名，无状态、可校验、不可伪造
- `reauth/start`：校验签名 → 创建特殊 OAuth state（绑定 integrationId，类型标记 `reauth`，不要求登录会话）→ 302 到飞书授权页
- OAuth 回调处理 `reauth` 类型 state 时：
  1. 用集成应用换取 token、读用户信息
  2. **本人校验**：飞书返回的 `open_id` 必须等于该集成已存储的 `authorizedOpenId`（同一应用内 open_id 稳定），不等则拒绝并提示"请使用原授权账号"
  3. 加密保存新 token（复用现有 `upsertFeishuAuthorization`）
  4. 为该集成 `userId` 重建浏览器会话（`createSession`，见下方说明）
  5. 重跑检查、重启事件监听（复用 `integrationSetup` / `integrationActivationService` 现有能力）
  6. 触发 4.4 的自动补发
  7. 跳回配置向导页 `/feishu-config?oauth=success`（有会话则显示该集成校验通过、状态正常）
  8. 机器人向用户推送授权成功确认卡："✅ 授权成功！你之前的会议报告正在补发中，稍后推送给你。"（复用 IM 通道，应用凭证发送）
- **会话决策（已与本人确认）**：会议分析主链路（事件→门槛→分析→报告推送）全部依赖服务端凭证与数据库 token，本身不需要浏览器会话；但落地页定为配置向导页，该页依赖会话识别用户——无会话会被当作新用户重新显示「创建应用」并可能走进"账号已绑定"死路。因此重建会话是"配置页落地"的必要配套，与主链路无关

### 4.4 授权成功后的自动补发

- 触发点：reauth 回调成功保存 token 后（普通向导授权路径不触发）
- 筛选：`meeting_pipeline_tasks` 中该集成 `status='blocked'` 且 `payload->'gate'->>'reasonCode'` 以 `oauth_` 开头的任务
- 90 天窗口：`payload->'telemetry'->>'eventReceivedAt'` 距当前 ≤ 85 天（留 5 天余量）的重新入队（`status='pending'`、`next_run_at=now`、清租约与错误、`attempt_count` 归零）；超窗任务标记 `skipped`（reasonCode `expired_beyond_recovery_window`），不补发
- 恢复操作必须写审计：`meeting.pipeline.auto_resume`（operator=system、taskId、integrationId、原 reasonCode）
- 事务边界：批量恢复与"授权成功"落库不要求同事务，但单个任务的状态重置必须原子；恢复后由 Worker 正常领取，重复事件不会重复分析（既有唯一键与 completed 保护不变）

### 4.5 约束与不变量

- 不改变 ABC 门槛、owner 校验、初始化校验的任何语义；补发的会议仍须完整通过资格检查
- 敏感信息：提醒消息与审计日志不含 token/secret；签名令牌不含可逆信息
- 审计：提醒发送、reauth 发起/完成、自动恢复均落 `feishu_audit_logs`
- 不引入新的全局单例；定时/状态以数据库为准（本次无主动扫描任务，无需新表、无 DDL 预期）

## 5. 不做的事（明确排除）

- 不做方案 A（到期前定时扫描预防式提醒）
- 不为其他原因（非 oauth_*）的 blocked 任务提供前端恢复按钮；保留管理员手动 SQL 通道
- 不改动登录按钮（其存废另议）
- 不改动 Zone 判定、报告模板、Base 字段绑定

## 6. 验收标准

1. 授权失效集成的新会议：任务 blocked、reasonCode 为 `oauth_*`、无重试（任务不进入 scheduled）、无 meeting_record
2. 同一失效周期内多场会议：只收到一条提醒；恢复授权后再失效，可再次提醒
3. 提醒消息在飞书客户端可收到，链接在未登录/会话过期的浏览器中可完成授权；换他人飞书账号授权被拒绝
4. 重新授权后：blocked 任务自动重新入队并最终 completed，用户收到补发的报告通知；Base 记录正常回写
5. 超过 85 天的 blocked 任务标记 skipped，不补发、不再提醒
6. archived 项目的集成不发提醒
7. 全流程审计完整（提醒、reauth、自动恢复均可追踪）
8. `pnpm ts-check` / `pnpm lint` / `pnpm build` 通过；隔离测试覆盖上述 1–6

## 7. 实施拆解（建议顺序）

1. 资格检查捕获授权异常 → blocked（4.1）
2. 提醒服务 + 去重 + 项目截止（4.2）
3. reauth 免会话链路（4.3）
4. 自动补发（4.4）
5. 隔离测试 + 文档同步（`docs/飞书集成设计.md` 第 3/7 章、`docs/项目结构说明.md`）
