**前置条件**

- 当前分支的核心功能验证通过
- 关键问题没有新的阻塞性回归
- `lint`、`build`、关键手工链路验证已完成

**当前状态**

- 恢复 GitHub 登录后，执行顺序为：提交分支 → 推送分支 → 创建 Draft PR → 联调验证 → 审阅合并。

**完成标准**

### W2. 数据库会议报告持久化

**目标**

- 将当前“会议分析报告主要存放在飞书 Base 中”的模式，升级为“平台数据库中也有一份持久化报告记录”

**为什么要做**

- 当前报告链接主要依赖：
  - 飞书 Base 中的 `JSON数据`
  - `integrationId`
  - `orgTargetId`
- 如果用户后续删除飞书应用、授权失效、Base 权限变化，历史报告可能无法继续读取
- 历史会议分析结果本质上属于平台资产，不应只依赖飞书侧保存

**已完成代码**

- 新增飞书会议详情读取，保存会议名称、时间、主持人标识、会议状态和纪要 ID。
- 新增 `vc:meeting.meetingevent:read` 用户权限，不读取参会人。
- `meeting_records` 保存完整 `AnalysisResult`、随机稳定的 `report_public_id` 和内部错误。
- 新增 `/report/<report_public_id>` 永久报告页，已持久化报告不再依赖飞书应用、OAuth 或 Base。
- Base 面向用户只保留会议信息、处理状态、文字稿、摘要和永久报告链接；新流水线停止写入 `JSON数据`、`错误信息`。
- 飞书消息展示会议名称、会议时间和永久报告按钮，不展示会议 ID。
- Base 同步失败重试时复用数据库中已经完成的分析结果，不重复调用大模型。
- 新增默认 dry-run 的历史回填和 Base 字段迁移脚本。
- 新增会议详情、报告持久化、Base 同步、任务重试和报告读取的结构化日志及审计记录。

**采用方案**

```text
Supabase meeting_records = 报告长期事实来源
飞书 Base = 组织协作入口和报告索引
飞书应用 = 新会议监听、详情/妙记读取、Base 同步和消息通知
```

**尚未完成**

- 尚未创建和合并 PR。
- 尚未在线上执行 Supabase migration。
- 尚未为旧 Base 创建新字段。
- 尚未执行历史报告 dry-run 和正式回填。
- 尚未删除旧 Base 的 `JSON数据`、`错误信息`。
- 尚未验证删除飞书应用、OAuth 失效、容器重建和数据库恢复后的历史报告访问。
- 尚未完成真实会议详情权限和 90 天/归属限制的线上验证。

**价值**

- 历史报告不再完全依赖飞书应用和 Base
- 平台可以独立保留会议资产
- 更适合后续做搜索、统计、权限治理和长期归档

### W3. 前端页面增加会议反馈

**目标**

- 在前端页面内增加“反馈问题 / 会议反馈”能力，便于用户直接提交初始化体验问题、自动分析异常和报告使用反馈

**为什么要做**

- 当前如果用户遇到问题，只能通过口头、截图或外部表单描述
- 反馈与系统上下文没有自动绑定，排障效率低
- 后续如果给更多人使用，需要一个更标准的反馈入口

**已完成**

- 配置页增加反馈按钮和轻量弹窗。
- 用户开始创建应用并获得系统会话后即可反馈；匿名阶段不开放反馈。
- 桌面端和移动端均提供入口，移动端入口位于 sticky 状态区，不会随步骤滚动消失。
- 新增 `/api/feedback` 和 `user_feedbacks` 数据表。
- 自动保存用户、集成、组织、页面、步骤和必要的追踪上下文，用于与结构化日志对应。
- 反馈内容和运行上下文落 Supabase，不要求用户手工填写技术信息。

**价值**

- 用户遇到问题时可以直接在系统内反馈
- 反馈能自动带上日志定位键
- 后续可以形成初始化与会议体验问题台账

### W4. 同一会议幂等与跨 integration 去重

**当前已实现**

- 相同 `integrationId + eventId` 被视为飞书重复投递并直接跳过。
- 相同 `integrationId + meetingId` 只能有一个任务和一份持久化会议记录。
- 同一进程使用 `integrationId + meetingId` 处理锁，避免同时重复调用文字稿和大模型。
- 同一会议重试复用原 `report_public_id` 和已经保存的分析结果。
- Base 在目标表内按 `会议ID` 查找并更新已有记录。

**待修正的代码边界**

- 已完成会议收到新 `eventId` 时，当前任务会被重置为 `pending`。
- 流水线随后发现 Base 状态为 `已完成` 并跳过分析，但还需要同步把数据库任务恢复为 `completed`，避免留下状态不一致的任务。

**待产品确认**

当前跨 integration 不去重：

```text
integration A + meeting X = 一条任务
integration B + meeting X = 另一条任务
```

如果两个 integration 绑定同一个组织 Base，当前可能重复读取文字稿、重复分析或竞争写入同一会议记录。需要确认目标规则：

1. 同一组织中的同一会议只分析一次；或
2. 每个用户 integration 各自分析一次。

如果选择“同一组织只分析一次”，建议数据库业务唯一键调整为：

```text
org_target_id + feishu_meeting_id
```

不同组织仍可各自保留一份报告。产品结论确认前，不修改现有唯一约束，避免误合并本应独立的报告。

**完成标准**

- 修复完成态重复事件造成的任务状态不一致。
- 产品确认跨 integration 去重规则。
- 根据结论补充数据库迁移、并发测试和重复事件日志验证。
