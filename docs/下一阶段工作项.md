## 3. 详细工作项

### W1. PR 合并主干

**目标**

- 当当前分支验证通过后，将已完成的分析链路迁移、飞书主链路修复和相关文档同步内容合并回 `main`

**前置条件**

- 当前分支的核心功能验证通过
- 关键问题没有新的阻塞性回归
- `lint`、`build`、关键手工链路验证已完成

**建议执行步骤**

- 复核本分支与 `main` 的差异范围
- 确认需要进入主干的提交集合
- 在 GitHub 发起或整理 PR
- 补充本轮改动说明与验证结论
- 合并后在服务器或目标环境更新到主干

**风险点**

- 如果仍有未确认的主链路问题，过早合并可能把风险带进主干
- 如果主干已有新提交，需要注意合并后的回归验证

---

### W2. 数据库会议报告持久化

**目标**

- 将当前“会议分析报告主要存放在飞书 Base 中”的模式，升级为“平台数据库中也有一份持久化报告记录”

**为什么要做**

- 当前报告链接主要依赖：
  - 飞书 Base 中的 `JSON数据`
  - `integrationId`
  - `orgTargetId`
- 如果用户后续删除飞书应用、授权失效、Base 权限变化，历史报告可能无法继续读取
- 历史会议分析结果本质上属于平台资产，不应只依赖飞书侧保存

**当前现状**

- 项目中已有单独规划文档：
  - [报告持久化改造计划.md](./报告持久化改造计划.md)
- 但该方案尚未正式实施

**建议实施方向**

- 在数据库中新增会议报告持久化表，存储：
  - 会议基础信息
  - transcript 或 transcript 摘要
  - `analysisResult` JSON
  - 关联 `integrationId`、`orgTargetId`、`meetingId`、`recordId`
- 报告页优先从平台数据库读取
- 飞书 Base 作为外部同步副本或外部查看入口，而不是唯一事实来源
- 需要明确历史兼容策略：
  - 老记录如何迁移
  - 新记录如何双写
  - 报告页如何优先读库、必要时 fallback

**价值**

- 历史报告不再完全依赖飞书应用和 Base
- 平台可以独立保留会议资产
- 更适合后续做搜索、统计、权限治理和长期归档

### W3. 前端页面增加会议反馈

**目标**

- 在前端页面内增加“反馈问题 / 会议反馈”能力，便于用户直接提交初始化体验问题、自动分析异常和报告使用反馈

**为什么要做**

- 当前如果用户遇到问题，只能通过口头、截图或外部表单描述
- 反馈与系统上下文没有自动绑定，排障效率低
- 后续如果给更多人使用，需要一个更标准的反馈入口

**建议方向**

- 在初始化配置页、报告页或关键错误提示处增加“反馈问题”入口
- 第一版不让用户拆字段填写，只保留一个问题描述输入框
- 输入框中的示例文案提示用户尽量描述：
  - 问题发生阶段
  - 看到的现象或报错
  - 具体影响
- 系统自动附带：
  - `userId`
  - `integrationId`
  - `orgTargetId`
  - 当前页面
  - 当前步骤
  - `setupTraceId` / `taskId` / `recordId` 等上下文
- 这些上下文的主要作用是帮助排查时将用户描述与结构化日志对齐，不要求用户手工填写
- 反馈记录落到一张专用 Base 表或平台数据库表中

**建议先做的最小版本**

- 在 `FeishuConfigWorkspace` 页面内增加反馈按钮
- 做一个轻量弹窗表单
- 新增反馈 API 路由
- 把结构化反馈写入一张专用表

**价值**

- 用户遇到问题时可以直接在系统内反馈
- 反馈能自动带上日志定位键
- 后续可以形成初始化与会议体验问题台账
