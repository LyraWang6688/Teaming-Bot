# 飞书自动分析链路待优化项清单

> 最后更新：2026-07-24
> 目标：整理当前已确认的 12 个待优化项，作为后续分批改造的统一依据。

## 1. 文档说明

本文档覆盖当前“飞书自动分析主链路”和“飞书配置初始化体验”中，已经通过日志、页面表现或代码核对确认的待优化项。

这些问题目前**不阻塞核心功能闭环**：

- 飞书初始化可以完成
- 事件可以接收
- 妙记文字稿可以导出
- 分析可以写回 Base
- 报告页可以打开

但这些问题会对以下方面产生影响：

- 幂等与并发安全
- 系统稳定性
- 运维排障效率
- 用户体验与可理解性
- 长期可维护性

## 4. 详细问题清单

### T1. 同一会议被多个 integration 重复消费、重复入队

**现象**

- 同一个 `meetingId` 会被两个不同的 `integrationId` 同时收到
- 两边都会执行 `minute_generated_event_received`
- 两边都会绑定到同一个 `orgTargetId`
- 两边都会分别创建 `meeting_pipeline_task`

**日志证据**

- 同一会议 `7665333446604213513` 同时被：
  - `ac56757f-2085-4a1d-a794-d75451f59df4`
  - `96a8e005-e48c-461b-8533-971641c1e0ac`
  接收并分别入队
- 同一会议 `7665362367174184115` 再次复现同类问题

**根因判断**

- 当前任务幂等主键落在 `integration` 维度，而不是业务目标维度
- 当前唯一约束本质上是：
  - `integrationId + meetingId`
  - `integrationId + eventId`
- 这能防住同一 integration 内的重复投递，但防不住跨 integration 的重复消费

**当前影响**

- 重复事件消费
- 重复任务入队
- 重复查 Base
- 重复导出 transcript
- 浪费 worker 和飞书 API 调用

**当前兜底**

- 后置业务层幂等仍在生效
- 当其中一条任务先完成后，后来的任务会因为 `会议已完成分析` 被 skip

**风险**

- 如果两个任务时序更接近，未来可能出现双重分析或重复写回

**建议方向**

- 将任务唯一性提升到业务目标维度
- 优先考虑：
  - `orgTargetId + meetingId + eventType`
- 入队层改为数据库唯一约束 + `ON CONFLICT DO NOTHING`

### T2. 配置页初始化阶段存在重复查询

**现象**

- 初始化日志中短时间内多次出现：
  - `integration_list_succeeded`
  - `integration_detail_loaded`

**日志证据**

- 在初始化完成前后，`12:51:40` 到 `12:52:10` 之间出现多次 list/detail 请求

**根因判断**

- 当前不是单一轮询器问题，而是多个动作叠加：
  - 创建应用轮询
  - 授权轮询
  - 自动检查触发
  - 检查完成后再次刷新 detail

**当前影响**

- 日志噪音大
- 额外数据库查询
- 额外接口调用
- 影响排障可读性

**建议方向**

- `loadIntegrationDetail()` 增加最短刷新间隔或请求复用
- `allPassed=true` 或完成态后减少无意义刷新
- 轮询改为退避策略
- 长期可评估 SSE / WebSocket 推送状态

### T3. 部分 integration 在导出妙记 transcript 时出现 403 权限失败

**现象**

- 主链路可以收到事件、入队、写 Base 记录
- 但在导出妙记文字稿时失败

**日志证据**

- `GET /open-apis/minutes/v1/minutes/{minuteToken}/transcript`
- 返回：
  - `403 Forbidden`
  - 业务码 `2091005`
  - `permission deny`

**根因判断**

- 当前 integration 对应的授权用户对该篇妙记没有 transcript 导出权限
- 这更偏向资源权限 / 授权主体问题，而不是分析链路代码故障

**当前影响**

- 该会议会停在 transcript 导出阶段
- 最终触发 `meeting_pipeline_failed`

**建议方向**

- 重新授权出问题的 integration
- 使用该 integration 对应用户发起新会议重新验证
- 补充更清晰的失败文案和后台定位信息

---

### T4. 日志存在敏感信息泄露风险，且部分错误事件命名不准确

**现象**

- 运行态错误日志中曾直接打印完整 `Authorization: Bearer ...`
- `transcript_export_retryable_error` 事件名与真实 `retryable=false` 的情况不一致

**根因判断**

- 底层错误对象被过度展开打印
- 错误事件名没有和最终可重试判断保持一致

**当前影响**

- 存在 token 泄露风险
- 会误导排障者对错误性质的判断

**建议方向**

- 对 token / secret / Authorization 统一脱敏
- 避免打印完整 axios/request 对象
- 将错误事件名改成中性命名，例如：
  - `transcript_export_failed`
- 是否可重试通过字段表达，而不是写死在事件名中

### T5. 低信息量会议下，报告第二部分和第三部分完全不展示

**现象**

- 某些飞书自动生成的报告只显示：
  - 第一部分：团队整体状态
  - 第四部分：领导者建议
- 第二部分与第三部分整段消失

**页面证据**

- 报告链接：
  - `/report?recordId=recvq79hnr7HsS&integrationId=96a8e005-e48c-461b-8533-971641c1e0ac&orgTargetId=5105f7c0-c700-443f-9d62-9849633bc915`
- 页面中未渲染第二、第三部分

**日志与数据特征**

- `transcriptLength` 很短
- 行为维度大量为 `Grey`
- `zone = Difficult to Judge`

**根因判断**

- 第二部分依赖 `dialogueNetwork.nodes.length > 0`
- 第三部分依赖：
  - `unfinishedDialogues.length > 0`
  - 或 `unseenDisagreements.length > 0`
- 当这些数据为空时，前端直接不渲染对应区块

**当前影响**

- 用户会误以为“报告缺了两部分”
- 无法判断这是“数据不足”还是“系统异常”

**建议方向**

- 即使数据为空，也保留第二、第三部分区块
- 显示“当前会议信息不足，暂无法生成该部分内容”的占位文案

### T6. 飞书应用被删除后的主动监控与恢复机制不足

**现象**

- 如果用户删除已授权飞书应用，系统当前不会在删除当下主动报警

**当前系统表现**

- 下次跑真实检查时，会在应用读取阶段失败
- 服务重启恢复 listener 时，启动会失败
- 调用飞书接口时，会报 OpenAPI 错误

**当前已有能力**

- 应用存在性检查
- 失败状态落库
- listener 启动门禁
- 审计日志与运行日志

**缺失点**

- 没有专门的周期性健康检查
- 没有“应用已被删”的主动预警机制

**建议方向**

- 增加周期性 integration 健康检查任务
- 主动校验：
  - 应用是否仍存在
  - listener 是否可恢复
- 失败后主动把集成标成降级状态，并在前端清晰提示

---

### T7. Token / 权限持续有效性缺少主动健康检查

**现象**

- 当前系统在真正调用接口时，能发现 token 失效或权限不可用
- 但缺少周期性、主动式的健康检查

**当前实现能力**

- Access Token 过期前会自动刷新
- Refresh Token 失效时会标记：
  - `reauthorization_required`
- OAuth scope 会在真实检查中比对
- 真实资源访问失败时会报错并落日志

**问题本质**

- 当前更偏“被动发现”
- 不是“持续监控”

**当前影响**

- 用户可能在真正使用时才发现授权已不可用
- 系统状态对用户来说不够前置透明

**建议方向**

- 增加后台周期性健康检查：
  - token 可刷新性
  - scope 完整性
  - 关键资源访问可用性
- 将异常状态前置到配置页中展示

---

### T8. 前端初始化流程与交互节奏仍需优化

**现象**

- 当前初始化流程虽然能跑通，但整体节奏偏紧、反馈偏碎
- 用户容易感受到步骤多、跳转多、状态刷新频繁

**问题表现**

- 页面状态更新较频繁
- 用户不容易区分：
  - 还在等待
  - 正在检查
  - 已通过但页面尚未收敛

**当前影响**

- 增加理解成本
- 提高误判“是不是出问题了”的概率

**建议方向**

- 收敛初始化阶段的状态刷新频率
- 优化“正在处理 / 已完成 / 需操作”的状态层次
- 弱化中间噪音状态，强化最终结果态
- 后续结合 T2 一并处理，提升整体初始化体验

### T9. 用户退出登录后再次点击登录出现 404

**现象**

- 用户在完成初始化链路后，右上角可以正常显示登录用户名
- 一旦退出登录，再点击前端“登录”按钮，会进入 404 页面

**页面证据**

- 用户退出后点击“登录”入口，页面显示：
  - `404 This page could not be found.`

**代码证据**

- [Layout.tsx](file:///Users/wangying/Documents/Codex/projects/src/components/Layout.tsx) 中，未登录态按钮跳转到：
  - `/login`
- 登录页组件位于：
  - [login/page.tsx](file:///Users/wangying/Documents/Codex/projects/src/app/login/page.tsx)
- 当前已能确认：这个问题至少是一个真实的产品表现问题，后续需要进一步核查：
  - 登录入口路径是否统一
  - 当前部署环境中登录页路由是否真实可达
  - 是否存在代理规则、构建缓存或部署版本不一致导致的 404

**当前影响**

- 用户一旦退出登录，就可能无法通过前端入口重新进入登录流程
- 对外部试用用户来说，这是明显的使用阻塞问题

**建议方向**

- 统一登录入口路径与回跳逻辑
- 增加“退出后重新登录”的回归验证
- 核查登录页路由、部署缓存和代理配置，避免路径在不同环境下失效

### T10. 当前服务器容量与并发承载能力未验证

**现象**

- 当前主要还是单人或极小规模测试
- 尚未验证 10 人、20 人甚至更多用户同时使用时的服务器稳定性
- 当前担忧点集中在：
  - 内存是否够用
  - 容器是否会被打爆
  - 分析任务并发时是否会拖垮服务

**问题本质**

- 这不是已经发生的线上故障，而是一个尚未完成验证的容量风险
- 当前系统同时包含：
  - Next.js 前端与 API 服务
  - 飞书事件监听长连接
  - 会议任务 worker
  - 豆包分析调用
  - 文件解析与报告渲染
- 当并发用户数、并发会议数、并发分析任务数上升时，CPU、内存、网络和外部 API 调用都可能成为瓶颈

**当前风险**

- 多个用户同时初始化、轮询和检查时，API 压力上升
- 多个会议同时进入自动分析时，worker、数据库与外部 API 调用会叠加
- 大文本会议稿并发分析时，内存峰值和响应时间可能显著上升
- 如果没有容量上限、并发控制和监控面板，问题可能先表现为：
  - 页面卡顿
  - 分析变慢
  - 容器重启
  - OOM
  - 飞书事件延迟处理

**当前缺失点**

- 没有系统化压测结果
- 没有明确的单机承载基线
- 没有完善的运行资源监控与告警
- 没有面向高并发的任务限流、排队和降级策略说明

**建议方向**

- 建立最小压测方案，分别验证：
  - 初始化配置并发
  - 网页上传分析并发
  - 飞书自动分析并发
- 输出单机容量基线，例如：
  - 同时多少个初始化请求
  - 同时多少个分析任务
  - 多大文本量下内存峰值是多少
- 增加资源监控：
  - CPU
  - 内存
  - 容器重启次数
  - 任务积压数
  - 平均分析耗时
- 后续补充并发控制与降级策略：
  - worker 并发上限
  - 排队机制
  - 超时与重试策略
  - 高峰期提示或限流

**建议细化**

- 最小压测方案建议分 3 轮：
  - 初始化并发压测：模拟多人同时进入配置页、触发检查与状态刷新
  - 上传分析并发压测：模拟多人同时上传 `.txt/.docx` 并创建分析任务
  - 飞书自动分析并发压测：模拟多场会议短时间内同时进入自动分析流水线
- 压测时至少记录：
  - 平均响应时间
  - 95 分位响应时间
  - 错误率
  - 容器 CPU / 内存
  - 任务积压数
  - 单场分析平均耗时
- 单机承载基线需要回答这些问题：
  - 同时多少个初始化请求仍能稳定响应
  - 同时多少个网页上传分析任务不会明显堆积
  - 同时多少个飞书自动分析任务不会明显拖慢主服务
  - 大文本会议稿在并发情况下的内存峰值大致是多少
- 建议先采用保守的并发策略，再逐步放开：
  - 飞书自动分析 worker 并发先限制为 1
  - 网页上传分析同时执行数先限制为 1
  - 同一 integration 的重复检查增加最短间隔或合并
  - 同一用户短时间内重复提交分析或检查时做节流
- 建议优先监控的资源与信号包括：
  - 容器 CPU 占用
  - 容器内存占用
  - 容器重启次数
  - `meeting_pipeline_tasks` 积压量
  - `web_analysis_tasks` 积压量
  - transcript 导出失败率
  - 分析平均耗时与失败率
- 所谓“并发控制与降级策略”，在本项目里的实际含义是：
  - 允许重任务排队，而不是无限同时执行
  - 高峰期优先保证自动分析主链路可用
  - 非关键轮询和刷新降低频率
  - 当系统繁忙时，优先返回“已进入队列，请稍后查看”，而不是让整个服务阻塞或崩溃

### T11. 移动端页面优化与移动端完成初始化配置的可用性不足

**现象**

- 当前系统主要按桌面端体验在推进和验证
- 但从产品使用场景看，用户很可能直接在飞书移动端或手机浏览器里进入配置页
- 目前尚未验证移动端是否能顺畅完成整条初始化链路

**问题本质**

- 从架构上说，飞书应用创建、OAuth、检查、监听启动都发生在服务端，因此“是否支持移动端完成配置”主要取决于：
  - 前端页面是否适配手机视口
  - 移动端下授权跳转和回跳是否顺畅
  - 组织选择、状态刷新、按钮交互是否足够清晰
  - 在飞书内打开网页时，页面是否存在兼容性问题
- 也就是说，移动端不是天然不能做，而是当前缺少专门的移动端适配与验证

**当前风险**

- 页面在手机上可能出现布局拥挤、按钮难点、状态信息过密
- OAuth 跳转、回调返回、再次进入配置页时，体验可能不连贯
- 用户即使理论上可以完成配置，实际体验也可能导致中途放弃或误判为系统故障

**建议方向**

- 对 `feishu-config` 页面进行响应式优化，至少覆盖常见手机宽度
- 针对移动端收敛信息密度，突出“当前步骤 / 需要做什么 / 是否完成”
- 专门验证这些链路在移动端是否可用：
  - 登录
  - 创建应用
  - OAuth 授权与回跳
  - 选择组织
  - 自动检查
  - 初始化完成提示
- 区分：
  - “移动端理论可用”
  - “移动端真实好用”
  并以真实手机环境或飞书内打开场景做回归验证

---

### T12. 前端初始化入口与授权方式需收敛为一条主路径

**现象**

- 当前在创建飞书应用、用户授权或进入初始化流程时，前端存在两种进入/授权方式：
  - 二维码
  - 网页链接
- 从产品体验上看，这两种方式并存会增加理解成本，也不利于后续对外统一说明

**问题本质**

- 当前还没有明确验证“哪一种方式对真实用户更顺畅、更少出错、更适合长期保留”
- 如果两条路径长期并存：
  - 用户会犹豫该选哪一种
  - 文案、指引、排障都要兼容两套说法
  - 前端体验难以收敛

**当前风险**

- 不同用户走不同入口，初始化体验不一致
- 出现问题时，难以快速判断是“链路本身问题”还是“入口选择问题”
- 增加帮助文档、页面说明和客服沟通成本

**建议方向**

- 把这条作为一个明确的前端体验优化项，而不是长期保留双入口
- 对比二维码和网页链接两种方式，至少从这些维度评估：
  - 到达率
  - 完成初始化成功率
  - 用户理解成本
  - 移动端友好度
  - 在飞书内打开时的顺畅程度
  - 出错后的可恢复性
- 最终收敛为：
  - 一个默认主路径
  - 另一个方式只保留为备用入口，或直接下线

**建议验证方式**

- 用真实测试用户各走一轮
- 分别记录：
  - 从进入页面到授权完成的耗时
  - 中途退出率
  - 常见报错类型
  - 用户主观反馈
- 基于结果决定长期默认保留哪一种方式

## 6. 当前结论

当前系统已经具备主链路可用性：

- 事件可以监听
