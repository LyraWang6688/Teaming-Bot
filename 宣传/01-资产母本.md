## 一、人设定位

### 1.1 一句话人设

> **我是一个人，用 AI 把一套真实运行在生产环境里的多租户系统，从 0 交付出来的人。**

不是"我会用 AI 写代码"，也不是"我做了个 AI 小工具"。卖点在于三个词同时成立：

| 关键词 | 含义 | 为什么值钱 |
|---|---|---|
| **一个人** | 产品定义、架构、前端、后端、数据库、部署、运维、文档、验收，全链路单点完成 | 大多数候选人只能讲清其中一段 |
| **真交付** | 已上线、有真实链路、有真实失败、有恢复机制、有审计 | 把"做过 demo"和"交付过系统"区分开 |
| **架构判断力** | 关键方案被自己推翻重来过，且每次都能说清"为什么推翻" | 这是 AI 时代最稀缺的能力：**AI 能写出代码，但选错方案没人替你负责** |

### 1.2 主张（对外反复讲的论点）

> **AI 已经把"写代码"的门槛降到很低，于是瓶颈整体后移了：从"能不能写出来"变成"知不知道该写什么、以及出了事谁来兜"。**
>
> 这套系统里最有价值的部分，恰恰全都不是 AI 主动会给我的：是显式依赖原则、是任务状态必须落库、是授权失效要能自动补发、是初始化必须五段门禁——**这些都是踩过坑之后长出来的判断，不是生成出来的代码。**

这个论点有三个好处：不吹 AI、不贬 AI、把功劳落在"判断力"上——**这是面试官会信、同事会服、读者会转的表述**。

### 1.3 反差点（叙事张力所在）

| 别人看到 | 实际是 |
|---|---|
| "一个会议纪要总结工具" | 一套多租户飞书集成 + 任务编排 + 受约束的两阶段 LLM 分析流水线 |
| "调个大模型 API 而已" | 证据提取与报告写作两阶段分离、`lockedDecision` 锁定不可改、引用必须原文可回溯 |
| "个人项目，随便做的" | 有 ADR、有验收报告、有整改清单、有启动恢复、有审计日志 |
| "AI 帮他写的" | AI 是执行者，方案是被他否决和重做过至少三轮的 |

## 三、故事主线

### 3.1 一句话主线

> **107 天，我一个人用意念（和 AI）把一套多租户系统送上生产；期间三次推翻自己的技术路线，两次线上事故，还有一次"把漂亮的理论标签亲手砍掉"。**

这条主线同时满足：有具体事件、有转折、有代价、有自省。**四个渠道都用它**，只是裁剪比例不同。

### 3.2 四幕结构（公众号/分享的骨架）

#### 第一幕 · 先做减法（06-17 ~ 06-26）

- 项目起点不是从零写代码，而是**接手一份已有代码然后砍掉一半**：收敛为 doubao-only + webhook-only，删掉 cozeProvider，统一生产管线（单次提交 36 文件、**净删 2600 行**）。
- 紧接着做多用户化：Supabase Auth、按 `integrationId` 路由 webhook token、飞书检查与 Base 初始化、解耦 worker、删除 `env` 兜底。
- **但立刻犯了一个错**：多集成功能做完没几天，又被自己删掉（`357a2c3` 删除多集成功能）。说明**当时做多账号太早了**。
- 📌 这一段的价值：证明他**会做减法、也会承认做早了**。

#### 第二幕 · 三次推翻技术路线（06-29 ~ 07-22）——**最强故事**

飞书接入方案在 5 周内被整体换掉三轮：

| 轮次 | 方案 | 为什么换掉 |
|---|---|---|
| ① | **Webhook 回调** | 需要公网暴露，多用户 token 路由复杂 |
| ② | **飞书 CLI（lark-cli）** | 以为"适合 Agent 调用的工具也适合做产品集成层"；结果 Dockerfile 连打 4 个补丁，部署成本不降反升 |
| ③ | **OpenClaw 设备流** | 想替掉分离的登录流程，但引入了新的外部依赖 |
| ④ | **飞书官方 Node SDK**（终局） | CLI 无法承担 **Token 全生命周期治理**（刷新、续期、失效判断） |

**决定性证据（可对外直接引用）**：SDK 迁移那一次提交 `e4aab30` 改动 **38 个文件，新增 2,035 行、删除 2,277 行——删得比加得多**；删掉了 `cliProfileManager`、`cliProcessStore`、`authDeviceCodeStore`，换来 `sdkClient` + `tokenService`。

- ADR-001 写下的结论：**"适合 Agent 的工具，不一定适合做产品集成层。"**
- 📌 这一段的价值：证明他**不是"能用就行"的人，而是在方案层做判断，并且愿意为判断付重构成本**。

#### 第三幕 · 交付危机：验收不通过（09-19 ~ 09-22）——**最有含金量**

首轮验收**结论：不通过**。F01–F08 共 8 项问题（P1×3、P2×5）。三个最狠的：

1. **报告已落库，交付却永久丢失**：报告先独立提交，之后才登记 Base/通知任务；跨表写入不在同一事务，登记失败只降级为一条日志。**用户永远收不到，重启也不补偿**。
2. **租约清空了才想重排，新版本必然丢**：V1 同步中 V2 入队 → V1 完成后 V2 永远留在库里；`requeueDeliveryTask` 因租约不匹配更新 0 行，**调用者不检查返回值，却写了一条"重排成功"的日志**。
3. **17 条僵尸任务与 20 分钟锁 TTL 完全吻合**：启动时先起 worker 再跑 startup recovery，两条路径并发处理同一任务，命中进程锁后直接 return 且**不收敛任务状态**；`meeting_records` 已是终态，两张表状态分叉。

还有一次安全事件：**连 SDK 错误对象都把完整 `Authorization: Bearer ...` 打进了日志**。修复覆盖 6 处 SDK 构造，并用**哨兵密钥**做替代测试证明输出无泄漏。

- 📌 这一段的价值：**这是全项目最值钱的部分**。绝大多数候选人只能讲"我做了什么功能"，他能讲"我的系统出过什么事故、我怎么定位、我怎么改架构、以及我承认历史日志里的凭据副本不会因为代码修复而消失"。

#### 第四幕 · 承认边界（09-30 ~ 10-04）——**最能体现成熟度**

- **真实线上事故**：`refresh_token` 有效期 7 天、仅"有活动"时才续期；2026-09-30 部署后，**他自己的两个集成掉线**，事后查明恰好是部署前 17 小时过期。
- 根因不是"忘了刷新"，而是**异常分类错了**：`FeishuAuthorizationError` 没被资格检查捕获，冒泡到通用 catch 被当成"临时错误"重试 3 次——每次都必然失败；最终 failed，用户无通知，恢复只能人工跑 SQL。
- 修复方案有四层：不重试 + 映射为 `blocked`；用**集成应用机器人**（`tenant_access_token` 与失效的用户 token 无关）当场私信通知；签名令牌实现**免会话重授权**；授权成功后 85 天窗口内自动补发。
- 同时期他做了**理论减法**：把 `Bion 群体动力学` 从实际判定逻辑中彻底移除（V2 提示词已无），并承认"理论写在简介里很漂亮，写进判定逻辑才叫产品"。
- ADR 里主动写下能力上限：**"宿主未运行时无法在宿主会话内送达，这是事实的直接后果，不可通过工程手段消除。产品表述必须诚实，不得承诺'随时推送'。"**
- 📌 这一段的价值：**知道自己系统的物理边界，并拒绝向用户过度承诺**——这是高级工程师和管理者的分水岭。

### 3.3 暗线（比主线更打动人）

**08 月整月只有 1 次提交。** 项目停摆了一个月（`3ea4f17` 仅隐藏了手动分析入口）。

然后 09 月回来做了 **49 次提交**，并经历了整个项目最大的一次改造（`424eed1`，+3,122/−662 行、23 个文件）和一次**验收不通过**。

> **个人项目的真相不是"我一直很努力"，而是"我停了一个月，然后又回来了"。**

这条暗线建议**只用于公众号和公开分享**——它建立的是"人"的信任，不是"工程师"的信任。

### 3.4 元叙事（你人设的核心证据）

仓库里有 **5 个 PR（#1–#5）来自 `codex/*` 分支**（如 `codex/persist-meeting-reports`、`codex/feishu-config-ui-polish`）。

这不是"AI 替我做了项目"，而是：

> **我定义问题、我选方案、我否决方向、我验收结果；AI 负责把决定变成代码。**
> 证据就是：**AI 不会主动建议我"把 2277 行删掉换成 SDK"，也不会主动告诉我"你的登记失败只写了一条日志"。**

### 3.5 ⚠️ 最关键待确认事实：这个项目的**起源真相**

调研发现三条硬痕迹，**它们决定你对外该怎么开口**：

1. `docs/2026-09-19-Teaming-Bot-首轮验收报告.md` 记载：交付说明来自 Notion 的 **「Trae code 交付说明」**，且报告写明"可直接复制到 Notion 作为执行 AI 的整改清单"。
2. 同期文档名为《2026-09-19-整改**接手**行动清单》——"接手"二字说明存在**前置交付方**。
3. Git 身份不唯一：`lyra` 128 次 / `winnie6688` 20 次 / `Lyra Wang` 7 次；另有 4 次提交作者为 `coze.cn` 平台；`codex/*` 分支来自 Codex。

**这三种可能的真相，说法完全不同，必须你来确认：**

| 情形 | 对外该怎么讲 |
|---|---|
| **A. 你从零主导，用 Trae/Codex 等工具生成代码，自己整改与验收** | 直接讲 §3.4 元叙事："我定义、我决策、我验收，AI 执行" |
| **B. 前序由外部（同事/外包/另一个 AI 工作流）交付，你接手整改与上线** | 讲**接手故事**："我接手了一套 AI 写出来的代码。它能跑，但上不了线——首轮验收不通过，8 个问题，3 个 P1。我花了一个月把它变成能上线的系统。"（这版**更强**） |
| **C. 混合**（部分模块来源不同） | 按模块讲清归属，不回避 |

> **无论哪种，都不要说"这是我从零一个人手写的"。** 仓库里的 Notion 引用、AI 平台提交、`接手`文档都会留下痕迹；主动说清反而是加分项——**面试官最怕的不是"你用了 AI"，而是"你讲的和代码里看到的不一样"**。

| "为什么代码量这么大但用户这么少？" | 讲**你在为多租户与可恢复性付成本**，以及事后看哪些是过度设计（例如过早做多账号，几天后又删掉） |
| "有测试吗？" | 直说 3 个文件 / 27 个用例、故障注入未落地，并给出你的补课计划与优先级理由 |

### 4.5 诚实边界清单（**面试加分项，不是减分项**）

主动说出以下限制，比被追问出来强一百倍：

- **测试长期为 0**：验收文档里写明"测试（当前为 0，验收硬门槛）"；现状是 3 个文件 / 27 个用例，计划中的故障注入用例未落地。
- **从未实现严格 exactly-once**：未做任意长任务的租约心跳/fencing，20 分钟锁仍是运行上限假设。
- **多段录制不支持**：每集成每会议一个任务的模型保留，同会议多段录制需另行设计。
- **历史数据不追溯**：不做历史批量补发，只处理新增。
- **已发送的卡片无法修正**：报告 URL 已在库里改正，但用户端旧卡片按钮不会自动更新。
- **验收缺真实链路证据**：当时"未执行真实会议、真实通知、生产故障注入"，只做到代码验收。
- **两个大设计仍是 Proposed**：AI 宿主接入设计、多用户闭环架构设计**均未实施**，ADR-002 仍是 Proposed。
- **历史凭据副本**：代码已修，但历史日志里的凭据不会因修复而消失。

> 用法：面试时**主动**说 2–3 条，并接一句"这是我下一步要还的技术债，我的判断是先做 X 因为 Y"。这比全说"没问题"可信得多。

## 八、面试锚点

> 面试的胜负不在"讲完项目"，而在"面试官愿不愿意往深里追"。以下 5 个锚点都是**能被追三层**的。

### 8.1 三分钟总述（口播稿，约 650 字）

> "我做的是一套会议动力分析系统，已经在生产环境跑着。业务上，它把飞书妙记的会议文字稿，用 Amy Edmondson 的 Teaming 框架做结构化分析，判断这个团队当前处在学习区、舒适区、焦虑区还是冷漠区，然后把报告回写到飞书多维表格。
>
> 技术上是 Next.js + Supabase + 飞书官方 SDK + 豆包大模型，写了 107 天，153 次提交，大概 2 万 7 千行 TypeScript，23 篇设计文档。
>
> 但我想讲的不是这些数字，是**我推翻过自己四次**。
>
> 飞书接入方案我换了四轮：最先是 webhook，需要公网暴露；然后换成飞书 CLI，因为我觉得适合 Agent 调用的工具应该也适合做集成层；再试了设备流。最后整体迁到官方 SDK——那一次提交改了 38 个文件，**新增 2035 行，删掉 2277 行，删得比加得多**。因为 CLI 把凭据存在本地 profile 目录里，它承担不了 token 的全生命周期治理。
>
> 第二件事更疼。9 月做首轮验收，**结论是不通过**，8 个问题里 3 个 P1。最严重的一个是：报告已经落库了，但交付任务没登记成功——跨表写入不在同一个事务，登记失败只降级成一条日志。用户永远收不到报告，服务重启也不会补偿。我们后来还发现有 17 条任务长期卡在 running，节奏和 worker 锁的 20 分钟 TTL 完全吻合，根因是启动时两条路径并发处理同一任务。
>
> 第三件事是自己打自己脸。项目简介里我写过'基于 Bion 群体动力学'，后来我把代码里的它删了——因为**它从来没有真正参与过任何一次判定**。理论写在简介里很漂亮，写进判定逻辑才叫产品。
>
> 这些事教给我一件事：**AI 能把代码写出来，但没人替你的方案负责。** 我现在最看重的不是能不能写出来，是知不知道该写什么、以及出了事谁来兜。"

### 8.2 五个深挖锚点（按被追问概率排序）

#### 锚点 1｜为什么最后选官方 SDK（最高频）

- **一句话结论**：不是 SDK 更好用，而是**它是唯一能承担 token 全生命周期治理的方案**。
- **细节**：CLI 把凭据放在 profile 目录 → 不可治理；webhook 需公网暴露；设备流引入额外依赖。SDK 一个依赖收敛了建应用、OAuth、事件长连接、OpenAPI。
- **三连问预演**：
  - "为什么当初会用 CLI？" → 我当时误判了"适合 Agent 调用的工具也适合做产品集成层"（ADR-001 结论）。
  - "迁移成本多大？" → 38 个文件，净删 200 多行，删掉了 profile 管理、进程存储、设备码存储三个模块。
  - "现在满意吗？" → 有代价：SDK 版本被锁死，未封装的端点还要自己手写，错误对象必须脱敏后才能进日志。

#### 锚点 2｜"报告存了但用户收不到"（最能体现深度）

- **一句话结论**：**"数据已经成功"不等于"后续工作已经登记"**，事务边界必须覆盖交付需求。
- **细节**：报告先独立提交，之后才登记 Base/通知任务；登记失败只写日志；入口检测到 completed 就直接 return，重启不补偿。修复：四阶段全部进 `transaction()`，仓储层接受 `tx`。
- **三连问预演**：
  - "怎么发现的？" → 首轮验收按用例矩阵逐条走，发现库里有报告但无对应交付任务。
  - "为什么原来会这么写？" → 因为开发时按"功能"切分，而不是按"事务边界"切分。
  - "怎么防止复发？" → 把"跨表写入必须同事务"写成规格里的不可破坏约束，并在验收用例里覆盖。
- **诚实代价**：这属于上线前被自己抓住，不是生产事故。

#### 锚点 3｜状态机与"唯一事实来源"

- **一句话结论**：**进程内状态不能作为事实来源**，捡到过期锁就重跑必须配合状态收敛。
- **细节**：7 态任务 + `SKIP LOCKED` + 租约心跳；租约释放与 pending 判断必须是**一次原子更新**且**校验返回值**（原来更新 0 行却写了"重排成功"的日志）；17 条僵尸任务的节奏与 20 分钟 TTL 吻合。
- **三连问预演**：
  - "为什么用数据库做锁不用 Redis？" → 任务量与一致性优先级：数据库是唯一事实来源，减少一个需要保证一致性的组件。
  - "exactly-once 做到了吗？" → **没有，我明确不宣称**。未做任意长任务的租约心跳/fencing，20 分钟锁是运行上限假设。
  - "那你怎么保证不重复？" → 幂等键落在业务目标维度（冻结建任务时的 Base 目标），外加原子领取。
- **诚实代价**：承认未实现严格 exactly-once。

#### 锚点 4｜让大模型只做语义，把判定权交回代码

- **一句话结论**：**模型擅长取证，不擅长稳定分类**。所以先让代码锁定判定，再让模型写作。
- **细节**：两阶段——证据包提取（唯一一次理论判定）→ 代码锁定 `lockedDecision`（区域/相邻区/维度方向/参与者类型/主要功能/语义互动）→ 报告写作**不得修改任何锁定字段**；引用必须能在原转写逐字回溯，否则删证据并降级；发言者识别、发言占比、姓名对齐、互动频次合并全部由代码完成。
- **三连问预演**：
  - "模型判错了怎么办？" → 单维证据不足时不硬选：输出"可能是 X 区或 Y 区"，并把定位点落在分界线上——**宁可不定位，也不编造确定性**。
  - "怎么防止模型胡说？" → 质量门 + 引用回溯 + 降级到基础事实版（只有文件无法解析、文本过短、发言者 <2 才阻止生成）。
  - "为什么不用分数？" → 分数诱导算术和横向比较；色标表达的是**证据质量**，Grey 是"看不见"而不是"中等"。

#### 锚点 5｜授权静默失效（有真实生产实证）

- **一句话结论**：**对必然持续失败的错误重试，只是在浪费调用，并且骗自己。**
- **细节**：`refresh_token` 7 天、仅"有活动"时续期；线上两个集成掉线，恰在部署前 17 小时过期。根因不是忘了刷新，而是 `FeishuAuthorizationError` 没被资格检查捕获，冒泡到通用 catch 被当成临时错误重试 3 次，每次必然失败，最终 failed 且用户无通知，只能人工跑 SQL。
- **修复四层**：异常分类为 `blocked` 且**不重试**；用集成应用机器人（`tenant_access_token`，与失效的用户 token 无关）当场私信；签名令牌免会话重授权；授权成功后 85 天窗口内自动补发。
- **三连问预演**：
  - "为什么要主动私信用户？" → 因为静默失败比失败本身更伤信任。
  - "怎么保证通知能发出去？" → 用 tenant token 的机器人通道，与失效的用户 token 解耦。
  - "还有什么没解决？" → 提醒本身仍依赖事件到达；`APP_ENCRYPTION_KEY` 没有轮换设计。
