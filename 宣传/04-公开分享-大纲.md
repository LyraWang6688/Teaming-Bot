## 一、选题定位

### 标题方案

**主推**：
> # AI 能写完代码，但没人替你的方案负责

**备选**：
- 《首轮验收不通过：一个上线系统的五次自我推翻》
- 《新增 2035 行，删掉 2277 行：技术选型里那些"看起来没问题"的决定》
- 《我把 Bion 从代码里删了：理论、AI 与工程的边界》

### 一句话主张（开场 30 秒内必须说出来）

> **AI 把"写代码"的门槛降到很低，于是瓶颈整体后移了：从"能不能写出来"，变成"知不知道该写什么、以及出了事谁来兜"。**
>
> 我今天讲五个我踩过的坑，它们全都是**判断问题**，不是编码问题。

### 目标听众与收获

| 听众 | 他们带走什么 |
|---|---|
| 工程师 | 五条可直接复用的工程原则（事务边界、状态收敛、异常分类、异常脱敏、理论减法） |
| 技术管理者 | "AI 参与交付后，验收门禁应该加在哪里"的实操答案 |
| 产品/业务 | 一个真实系统从"能跑"到"能上线"之间到底差什么 |

## 三、逐页要点

### 第 1 页｜钩子：一个用户永远收不到的报告（1.5 分钟）

**屏幕**：只有一行字。

> 报告已经写进数据库了。
> 但用户永远收不到。
> 而且重启也不会补偿。

**口播要点**：
- 不要先介绍自己，不要先介绍项目。
- 直接讲：这套系统当时已经在生产跑着，能收事件、能调模型、能出报告。从外面看，它"做完了"。
- 停顿。然后说："我们是在一次验收里发现这条路径的。失败没有报错，没有告警，只在日志里留了一行字。"
- 收口过渡："这个故事里有五个坑，我今天全讲完。"

**讲者备注**：这一页的作用是**建立信任**——一个愿意公开自己失败的人，后面讲方法论才有人信。

---

### 第 2 页｜我做了什么（2.5 分钟）

**屏幕**：数字条 + 一张报告页截图（**匿名模式**）。

```
107 天  ·  27,115 行 TypeScript  ·  22 个 API 端点  ·  153 次提交
```

**口播要点**：
- 系统一句话：把飞书妙记的会议文字稿，用 Edmondson 的 Teaming 框架分析，判定团队处在学习区/舒适区/焦虑区/冷漠区，报告回写多维表格。
- **只讲 30 秒，然后立刻转折**："但今天重点不是这个系统，是我在这 107 天里做错的判断。"
- 如果有真实使用量且已确认可公开：说"累计分析约 200 场真实会议"，**必须紧跟**"但真实活跃用户规模还很小，目前是验证阶段"。

**讲者备注**：数字条的目的是让听众**不用怀疑你的执行力**，从而把注意力放在判断力上。不要逐条念。

---

### 第 3 页｜四次推翻：方案选型怎么判断（4 分钟）

**屏幕**：四行表格（webhook → CLI → 设备流 → 官方 SDK），最后一行高亮。

| 轮次 | 方案 | 活不下来的原因 |
|---|---|---|
| 一 | Webhook 回调 | 需公网暴露，多用户凭据路由复杂 |
| 二 | 飞书 CLI | 误判"适合 Agent 调用的工具也适合做产品集成层" |
| 三 | 设备码流程 | 引入新依赖，问题没少 |
| 四 | 官方 Node SDK | 终于能管 token 全生命周期 |

**口播要点（关键数据在这里砸）**：
- "第二轮到第四轮那次迁移：**38 个文件，新增 2035 行，删除 2277 行。删得比加得多。**"
- "删掉的是我自己写的三个模块：profile 管理器、进程存储、设备码存储。"
- **结论句**（放慢，重复一次）："**适合 Agent 调用的工具，不一定适合做产品级集成层。**"
- 解释原因：CLI 把凭据存在本地 profile 目录，一次性调用很方便，但一个 7×24 响应事件、要判断凭据过期、要自动续期的服务，凭据放在文件系统里就不叫可治理。
- **坦诚代价**："我不后悔这次重构，我后悔的是第二轮做了三周。"

**讲者备注**：这一页最容易被追问"你怎么知道该换了"。准备好答案：**判断标准不是"新方案更好用"，而是"旧方案有结构性缺陷"**。

---

### 第 4 页｜最疼的一次：静默失败（4 分钟）

**屏幕**：两栏对比——左边"看起来正常的四步"，右边"连起来的结果"。

```
① 分析完成，报告落库（独立提交）
② 再登记回写/通知任务
③ 登记失败 → 只写一条日志
④ 下次进来看到"已完成" → 直接 return
────────────────────────────
结果：报告在库里，用户永远收不到，恢复机制再也不碰它
```

**口播要点**：
- 根因：**事务边界画错了**。我是按"功能"切分模块的，不是按"业务后果"。
- 修复：四阶段全部进同一个事务，仓储层显式接受事务对象。
- **原则句**："判断事务边界的问题不是'谁调用谁'，而是'**哪个写入失败之后，另一个写入就失去了意义**'。"
- 再补两个具体事故，证明这不是孤例：
  - **17 条僵尸任务**：长期卡在运行态，节奏与 worker 锁的 20 分钟 TTL 完全吻合；根因是启动时两条路径并发处理同一任务，命中进程锁后**不收敛状态**。
  - **"日志说成功、数据没变"**：释放租约后想用旧租约重排，更新影响 0 行，而调用者没检查返回值，还写了一条"重排成功"的日志。
- **金句**（放慢）："**日志说成功、数据没变，这是最危险的静默丢数据。它比报错危险得多，因为报错会有人查，成功日志不会。**"

**讲者备注**：这是全场最有价值的一页。如果时间不够，宁可砍第 5 页。

---

### 第 5 页｜让模型取证，把判定权交回代码（3.5 分钟）

**屏幕**：三格流水线图。

```
① 证据提取（模型）  →  ② 判定锁定（代码）  →  ③ 报告写作（模型，禁止改判）
```

**口播要点**：
- 核心判断：**模型擅长取证，不擅长稳定分类**。同一份会议记录让它"自由发挥"两次，结论会漂。
- 做法：第一阶段模型只提取可观察事实并完成唯一一次理论判定；随后由代码锁定区域、相邻区域、维度方向、参与者类型、互动功能；写作阶段**不允许修改任何锁定字段**。
- 兜底：报告里的每条引用必须能在原文字稿中逐字回溯，否则删除该证据并降级；发言者识别、发言占比、姓名对齐、互动频次合并**全部由代码完成**。
- **反直觉的细节**（听众会记住这个）：证据不足时不硬选区域，而是输出"可能是 A 区或 B 区"，把定位点画在分界线上——**宁可不定位，也不要编造确定性**。

**讲者备注**：这一页对做 AI 应用的听众吸引力最大。可以补一句"为什么不用分数"：分数诱导算术和横向比较，色标表达的是**证据质量**。

---

### 第 6 页｜承认边界：我删掉了一个很漂亮的理论标签（2 分钟）

**屏幕**：一句被划掉的字。

> ~~基于 Edmondson Teaming 框架 + **Bion 群体动力学**~~

**口播要点**：
- 我的项目简介里曾经写着"基于 Teaming 框架 + Bion 群体动力学"。
- 后来我发现：**Bion 在我的代码里从来没有参与过任何一次判定。** 它写在简介里，写在早期的一版提示词里，然后就再也没出现过。
- 我把它删了。
- **金句**："**理论写在简介里很漂亮，写进判定逻辑才叫产品。**"
- 顺带讲边界感：我的决策记录里明确写着，某项能力"不可通过工程手段消除，所以产品表述必须诚实，不得承诺'随时推送'"。

**讲者备注**：这一页是全场**人格分最高**的一页。它证明你不自欺，也不骗用户。

---

### 第 7 页｜五条原则 + 收尾（2.5 分钟）

**屏幕**：五条，一次性全部出现。

1. **"数据已经成功"不等于"事情已经办成"**——事务边界跟着业务后果画，不跟着模块画。
2. **日志说成功、数据没变，是最危险的静默丢数据。**
3. **换方案的理由不是"新方案更好用"，而是"旧方案有结构性缺陷"。**
4. **第三方 SDK 的异常是不受控输入。**
5. **对必然持续失败的错误重试，只是在浪费调用，并且骗自己。**

**收尾口播**（背下来）：

> "回到开头那个问题：这套系统从外面看是'做完了'的，为什么验收不通过？
>
> 因为它能跑通正常路径，**但没人在意异常路径**。而一个系统离'能上线'最近的那一步，恰恰就是从'正常路径能跑'到'异常路径有人管'。
>
> 至于 AI 在这件事里的角色——**它帮我把决定变成了代码，速度很快。但这五条，它一条都没有主动告诉我。**
>
> **AI 能写完代码，但没人替你的方案负责。**"

**讲者备注**：最后一句说完停两秒再进入 Q&A，不要马上说"谢谢大家"。

## 五、Q&A 预案

按被问概率排序。

| # | 问题 | 答案骨架 |
|---|---|---|
| 1 | **这是 AI 写的吗？** | 诚实 + 有力：编码环节大量借助 AI；但"方案被推翻、方向被否决、验收不通过"这三件事都不是 AI 主动提出的。**AI 不会建议你删掉 2277 行换成 SDK，也不会告诉你登记失败只写了一条日志。** |
| 2 | 团队几个人？ | 按真实情况回答；随后一句话界定你的职责范围（产品定义、方案选型、架构、验收、部署运维） |
| 3 | 为什么要重构四次？早期不能想清楚吗？ | 承认早期判断有误（这正是 ADR 存在的意义）；关键标准是**能识别旧方案的结构性缺陷**，而不是追新 |
| 4 | 你怎么保证消息不丢不重？ | **明确不宣称 exactly-once**；说清做到的部分（原子领取、租约、业务维度幂等键）与没做到的部分（租约心跳/fencing） |
| 5 | 为什么不用 Redis 做锁？ | 任务量级 + 一致性优先级：数据库是唯一事实来源，少一个需要保证一致性的组件 |
| 6 | 为什么选长连接不用 webhook？ | 事件是推送型的，服务端常驻；webhook 需公网暴露。代价：长连接不补发离线事件，需要对账兜底 |
| 7 | 大模型判错了怎么办？ | 证据不足时输出"可能是 A 或 B 区"并把点画在分界线上；引用必须原文可回溯，否则降级；只有极少数情况才阻止生成 |
| 8 | 有测试吗？ | 直说：3 个文件 / 27 个用例，故障注入未落地；给出你的补课优先级与理由 |
| 9 | 用户多吗？ | 真实回答 + "从能跑到有规模用户，还差的是什么" |
| 10 | 这套东西能商业化吗？ | 讲你的判断与已验证/未验证的假设，不要给估值式回答 |
