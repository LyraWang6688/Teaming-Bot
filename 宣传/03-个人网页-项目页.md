## 3. 项目背景（150 字，讲"为什么"）

> 团队协作的质量，往往藏在会议里那些"没说出口的话"里：谁敢提出反对、谁的问题没人回应、讨论在哪个点上停住了。
>
> 但会议纪要通常只记录"谁说了什么"，不记录"这些互动意味着什么"。
>
> 这套系统要解决的是后者：把一次会议的互动过程，映射成一个团队可以对照和讨论的状态判断——**不是给团队打分，而是给团队一面镜子**。

## 4. 它是怎么工作的（四步链路）

**版式建议**：横向四步流程图（可用 mermaid 或纯 CSS 步骤条）。

```
① 飞书妙记生成
   ↓  服务端长连接接收 minutes.minute.generated_v1 事件
② 资格校验与入队
   ↓  校验会议标题门槛、妙记所有者与授权身份一致
③ 两阶段分析
   ↓  证据提取（模型）→ 判定锁定（代码）→ 报告写作（模型）
④ 交付
   →  永久报告页 + 多维表格回写 + 机器人消息通知
```

**每一步的一句话说明**：

| 步骤 | 说明 |
|---|---|
| ① 事件接入 | 长连接订阅妙记生成事件，无需公网回调地址 |
| ② 资格校验 | 只分析符合条件的会议，且必须由妙记所有者本人发起 |
| ③ 两阶段分析 | 模型负责取证与写作，**判定权归代码**——写作阶段不允许改判 |
| ④ 交付 | 报告落库生成永久链接，回写多维表格，并以机器人身份推送 |

## 5. 三个技术亮点（**这节是面试官和同行真正会读的地方**）

### 亮点一：让模型取证，把判定权交回代码

- **问题**：大模型擅长理解语义，但不擅长**稳定分类**。同一份会议记录，"自由发挥"两次会给出不同结论。
- **做法**：两阶段流水线。第一阶段模型只提取可观察事实并完成唯一一次理论判定；随后**由代码锁定**判定结果（区域、相邻区域、维度方向、参与者类型、互动功能、语义互动）；第二阶段写作**不允许修改任何锁定字段**。
- **兜底**：报告中的每条引用都必须能在原文字稿中逐字回溯，否则删除该证据并降级；发言者识别、发言占比、姓名对齐、互动频次合并**全部由代码完成**，模型不参与。
- **态度**：当证据不足时，系统不硬选区域，而是输出"可能是 A 区或 B 区"，并把定位点画在分界线上——**宁可不定位，也不编造确定性**。

### 亮点二：任务状态以数据库为唯一事实来源

- **问题**：进程内状态（定时器 + Map）在重启后丢失，无法补偿，也无法观测。
- **做法**：7 状态任务机 + `SKIP LOCKED` 原子领取 + 租约心跳；重启后同领"到期任务"与"过期租约"。
- **踩过的坑**：曾出现 17 条任务长期卡在运行态，节奏与 worker 锁的 20 分钟 TTL 完全吻合——根因是启动时两条路径并发处理同一任务，且命中进程锁后未收敛状态。修复后启动恢复统一走原子领取。
- **原则**：进程内缓存只允许作为性能优化，**不能作为事实来源**。

### 亮点三：把"异常路径"当一等公民

- **事务边界**：报告落库与交付需求登记必须在同一事务内——否则会出现"报告在库里、用户永远收不到、重启也不补偿"的静默失败。
- **静默失败治理**：授权失效不再被当成临时错误重试，而是显式标记为阻塞、明确不重试，并用与失效凭据无关的机器人通道**主动通知用户**，再通过签名令牌实现免登录重授权。
- **凭据治理**：所有敏感字段统一加密落库、只在服务端解密；第三方 SDK 日志出口改为白名单摘要，并用哨兵密钥做替代测试验证无泄漏。

## 7. 我的角色（**建议保留这一节，它比技术栈更能建立信任**）

> **我负责的部分**：产品定义与判定逻辑设计、飞书接入方案的选型与四次重构、多租户架构、任务状态机与恢复机制、验收标准制定与整改、生产部署与运维、全部设计文档。
>
> **技术协作**：编码环节大量借助 AI 工具完成。可以明确的是——**方案被推翻、方向被否决、验收不通过这三件事，都不是 AI 主动提出的**。我在决策记录里写下的结论是："适合 Agent 调用的工具，不一定适合做产品级集成层。"

**为什么建议保留**：面试官和潜在合作方最想知道的不是"你会不会写代码"，而是"**出了事谁负责、方案错了谁来改**"。主动说清 AI 的参与边界，比含糊其辞更能建立可信度。
